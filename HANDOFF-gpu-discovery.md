2. **T2, the texture cache. Done: `gltexcache=449` (steps 2, 3, 4a, 4b and no record path in the main programs) is the default since 11-14.** Design: [docs/plan-t2-texcache.md](docs/plan-t2-texcache.md); numbers in PERF-NOTES "T2 probe", "T2 step 1", "T2 diagnosis", "T2 step 2".
   - **Why:** Mali counters showed the 3D shader is integer-bound (CVT 75–83% of core cycles), and the `gltexprobe` probe (debug, renders wrong on purpose) showed dropping the per-fragment texture decode takes −45% / −26% GPU cycles off W2 title / town on the Fold, −16% / −20% on the Pixel.
   - **How it works:** each texture is decoded once on the CPU (`GPU3D_OpenGLTexHeap.cpp`) into texel records (palette coordinate, integer alpha, kind) in a 16 MB RGBA8UI heap, kept until texture VRAM under it changes, plus `TexPalLinear`, a linear copy of palette RAM (so palette animation costs nothing). The shader's `TextureLookup_Cached` reads the record and runs today's float math, so output is bit-identical. The main programs are built without the old decode path (`TexCacheOnly`); polygons the heap can't serve (out of range, budget, volatile, heap full) get `RenderKey_TexFull` and draw with full-program twins `RenderShader[5..9]`, built lazily. A failed twin build turns the cache off until the switch changes.
   - **Results:** hash3d-exact on the desktop (7 scenes, mixed-path and check modes, state loads, resets, toggles, forced build failures) and on the Fold, Pixel and OnePlus. Fold −19% title / −10% town; Pixel −5.5% core-active (it throttles mid-run, so its any-queue and fps are unreliable). Steady-state CPU ~2–50 µs/frame; OnePlus graphics +0.7–1.9 MB.

## Known, left alone

- In pass 2, a matching-ID shadow turns blending on, and the next non-needopaque translucent polygon in pass 2 then blends when it shouldn't. Pre-existing; T1 keeps the same behavior.
- Pass 3 can blend an earlier translucent polygon over a later needopaque polygon's opaque pixel when the earlier one doesn't write depth (GL draws pass 2's results first). Pre-existing, not checked against software. Both are gone with `gltrans` bit 2 on a GPU with framebuffer fetch.
- Frames with a nonzero clear alpha still clear stencil to 0xFF, so translucent ID 63 can't draw over the clear plane there. `CountCoveredPixels`' `NOTEQUAL 0x7F` relies on that value.
- Desktop: Mesa GLES contexts (Intel/AMD) may list the EXT framebuffer-fetch extension, so the desktop build isn't always on the fallback. The startup log line shows it.
