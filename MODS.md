# Per-game mods (WideMelon + Lua)

Two mods, both set per game in ROM details → Mods tab and stored in `RomConfig.mods` (`RomModsConfig`): **WideMelon** widens the 3D view, and **Lua scripts** can read and change input and memory, draw on the screens and control a few emulator settings. Nothing runs unless it's switched on for that game. Paths below are under `app/src/main/` unless they start with `melonDS-android-lib/`; the core submodule has its own repo.

## Decisions to keep

- **Our own Lua API, no compatibility.** MelonMix (KHMelonMix's per-game C++ plugins) and DraStic script compatibility are dropped. DraStic's own Lua API readme (section 8) is a design reference only; DraStic is closed source, so there's no repo to point at. Old DraStic scripts get ported by hand.
- **RetroAchievements hardcore:** Lua is fully off, read-only scripts included (RA bans scripting outright). It's gated next to cheats (`impl/emulator/EmulatorSession.kt`), the Mods tab disables the switches and says why, and `melon.state.load` checks hardcore again anyway. WideMelon stays allowed: RA exempts widescreen hacks. Its one game-visible effect is that BoxTest is squeezed too (see "Known limits" under WideMelon).
- **One linked SAF folder per game**, picked in the Mods tab (`OpenDocumentTree`, persisted read permission), not copied. Top-level `.lua` files are the scripts; subfolders hold modules and images. New scripts start switched off. The app never writes to or deletes from the folder.
- Lua 5.4.9 from lua.org under `cpp/lua/`, unchanged except `cpp/lua/patched/lstrlib.c` (a work budget in pattern matching and plain find). `cpp/lua/LICENSE` says how to redo the patch on an upgrade.
- WideMelon is from pruefsumme's `melonDS-android-lib` `widemelon` branch, GPL-3.0-or-later, reworked (per-line wings rule, one width source, off-center viewports). It works on the OpenGL and Compute renderers; Software stays at 256 (see [docs/shelved/widemelon-software.md](docs/shelved/widemelon-software.md)).

## Script folder and the Mods tab

- `LuaScriptFolderSync` keeps `luaScripts` (file name, switch, options) in step with the folder: top-level `.lua` only, sorted by name. It runs when the Mods tab shows, when ROM details resumes, and at game start. A gone file's entry is dropped. If the folder can't be read (not a directory, provider throws, cursor still loading or errored, permission lost) the list is kept and the tab offers to pick the folder again.
- Changing or removing the folder clears the list and releases the permission, unless another ROM or one of the app's own folders (ROMs, BIOS, saves, perf log) uses the same tree. Picking the same folder again keeps the switches.
- At game start only switched-on scripts that exist are read (1 MB cap each) and sent to native with their options, storage blob, modules and images (`LuaScriptSetup` array over JNI). Native never opens script files. Edits take effect at the next game start.
- Header (`impl/LuaScriptHeaderParser.kt`, reads at most 8 KB of the leading comment block): `-- description: ...` is shown under the name (otherwise the block's first comment line). Options:
  ```
  -- option: speed type=number min=1 max=10 step=1 default=5 label="Aim speed"
  -- option: hud type=toggle default=true label="Show HUD"
  -- option: mode type=choice values=easy,normal,hard default=normal label="Difficulty"
  -- option: map_layout type=layout label="Layout while the map is open"
  ```
  At most 16 options; key `[a-z_][a-z0-9_]{0,31}`; label up to 60 chars; choice up to 8 values of up to 24 chars; numbers finite, min < max, at most 1000 steps. `step` defaults to 1; `default` to min, false or the first choice; an off-step default snaps to the nearest step. Unknown attributes or bad lines make the line unreadable, and the tab says how many were skipped. Layout options have no default and store a layout UUID ("Don't change" = none). Stored values are `RomLuaScript.options: Map<String, String>`; a missing or invalid value falls back to the default.
- Pause menu → Mods lists every script loaded this session with its description, error or "Switched off", plus scripts that couldn't be read (with the reason, can't be switched on). Switching off/on is for this session only and never changes the ROM config; on means a fresh state and `on_load`. "Options…" saves to the ROM config and restarts the script with the new values (its savestate slots are kept).
- Saved data: the Mods tab shows "Saved data: N KB" with Clear (ignored for the running game).

## Lua runtime

- `cpp/scripting/LuaEngine.{h,cpp}`, owned by `MelonInstance`, emulator thread only. One Lua state per script, 32 MB each. The engine file keeps the lifecycle and `setupScript`; the sandbox is `LuaSandbox.cpp` and each part of the module has its own file (`LuaMemoryApi`, `LuaDrawApi`, `LuaFolderApi` for `require` and images, `LuaStateApi`, `LuaStorageApi`, `LuaWideApi`), sharing the per-script state through the private `LuaEngineInternal.h`.
- Sandbox: only `base`, `table`, `string`, `math`, `utf8`. No `io`, `os`, `package`, `debug`, `dofile`, `loadfile`, `warn`; `load` takes text only; `print` goes to the log; `setmetatable` refuses `__gc`; `collectgarbage` only takes collect/count/step/isrunning; `string.rep` and `table.move/insert/remove/sort` have size caps.
- Limits per call: 1M instructions (10M for the main chunk plus `on_load`), and a work budget of 20 steps per instruction charged by pattern matching, table functions, allocation, drawing, storage and `require`. Once either runs out, everything left in that call fails, so `pcall` can't keep a script alive. An error or a limit switches the script off for the session and shows a message. The goal is that a buggy script can't freeze the game, not defense against a hostile one.
- When a script stops, the swap, controls, fast-forward and layout it set go back to the player's values (`ui/emulator/LuaUiOverrides.kt`, unit-tested). Newest request from a running script wins; a change the player makes by hand clears the requests and becomes the baseline. Fast-forward's baseline is off at each session start. Only a real player layout pick clears layout requests.
- Reset reloads every running script (`on_unload`, fresh state, main chunk, `on_load`); switched-off scripts stay off. Sticks are forwarded to native only while a script is active and zeroed when the last one stops.
- Events to Kotlin go through the native event pipe (one write, at most 512 bytes of data) and carry the script's index. Screen and fast-forward requests are coalesced per call; Kotlin applies them only when they differ from the UI's state.

### Callbacks

| Callback | When |
|---|---|
| `on_load(game_code)` | End of `MelonInstance::start()`, after the main chunk |
| `on_frame()` | Just before `nds->RunFrame()`. Input changes apply to this frame |
| `on_frame_end()` | After `RunFrame` (and the software upload), before the overlay upload. Own instruction budget; `melon.frame()` is the frame that just ran; `press`/`release` apply to the next frame |
| `on_state_loaded()` | On the emulator thread before the next frame after a savestate or rewind load (those run on IO/UI threads and only set a flag), or a script load |
| `on_unload()` | `stop()`, reset, switch-off; then the state is closed |

### API (`melon`)

- `melon.game.code()`, `melon.game.title()`, `melon.frame()`, `melon.log(...)` (logcat tag `melonade-lua`, only while the debug log is on; script errors are always logged).
- `melon.game.state()` → `"field"`, `"text"`, `"battle"`, `"fade"`, `"menu"` or `"off"` for a Pokemon game the native field read knows ("Pokemon game state" under WideMelon's Camera), nil for every other game. As of the last frame that ran (on the first call, or the first after a reset or state load, read from RAM right then). Calling it keeps the per-frame read on for the rest of the game, camera or not (`scripting/LuaGameApi.cpp`). No flying value: the field read has none.
- Input: `melon.input.held()`, `press(mask)`, `release(mask)` (last one frame), `touch()` → `x, y, down`, `set_touch(x, y)` (held until `clear_touch()`), `clear_touch()`, `stick("left"|"right")` → `x, y`. Final mask each frame is `(user & ~release) | press`; the UI's own `pressKey`/`releaseKey` are untouched.
- `melon.KEY.*` are ready-made masks, not bit numbers (`melon.KEY.R` is 256, so use it as is, not `1 << melon.KEY.R`). Pressed = bit set. Bits: A=0, B=1, SELECT=2, START=3, RIGHT=4, LEFT=5, UP=6, DOWN=7, R=8, L=9, X=10, Y=11, TOUCH=12. The engine flips it to the core's active-low mask.
- Memory: `melon.mem.read8/16/32(addr)`, `read_s8/s16/s32`, `write8/16/32(addr, v)`, and `melon.mem.arm7.*` with the same names. Goes through the NDS bus (JIT-safe, like AR cheats). ARM9 checks ITCM/DTCM first (ITCM writes invalidate the JIT). Reads in 0x04xxxxxx raise an error on both CPUs (I/O reads have side effects).
- `melon.screen.swap(bool)`, `show_controls(bool)`, `set_layout(key)`: `key` names a `type=layout` option; Kotlin resolves its UUID. `set_layout(nil)` goes back to the player's layout. A key that isn't a layout option is an error; "Don't change" or a deleted layout does nothing. Scripts see layout options in `melon.options` as a boolean (picked or not).
- `melon.screen.tilt_shift(top, bottom[, opts])`: blurs the DS top screen above and below a sharp band, whichever way the screens are swapped. `top` and `bottom` are that side's strength, clamped to 0..1; `(0, 0)` is off unless `color` is above 0 with a `saturation` or `contrast` other than 1. `opts = { center = 0.5, width = 0.3, radius = 6, saturation = 1, contrast = 1, color = nil }`: the band's center and height as fractions of the screen's height (0..1), the blur's radius at full strength at the screen's edge in DS pixels (0..12), and color multipliers (0..2, 1 is no change) for the whole DS top screen, sharp band included. `color`, clamped to 0..1, is how strongly those multipliers apply, whatever `top` and `bottom` are, so `tilt_shift(0, 0, { saturation = 1.3, color = 1 })` is only the color boost; absent, the boost follows the blur: the multipliers are scaled by `max(top, bottom)` so they fade with it. The same `color` gives the same picture with or without a blur. Safe to call every frame, since only a change sends an event. Newest running script wins, and a stopping script's blur goes away with it (`ui/emulator/LuaTiltShiftRequests.kt`, unit-tested). It's two passes after the filter's own (`VideoFilterPipeline.kt`, built on first use, skipped while off, the player's filter setting untouched) that run on the finished frame, so they blur 2D such as text too, but not `melon.draw`. With no blur to draw only the color boost runs, as one pass of one sample per texel, built on its own first use. Examples: `docs/examples/lua/tilt_shift_test.lua`, `docs/examples/lua/tilt_shift_platinum.lua`, `docs/examples/lua/tilt_shift_white2.lua` (in the last two the color strength follows the Blur strength option, so strength 0 means no boost; otherwise it stays on when the blur clears, in every game state, and only hold L, tap R fades it off).
- `melon.screen.bloom(strength[, opts])`: a glow on the bright parts of the DS top screen, whichever way the screens are swapped. `strength` is clamped to 0..2; 0 is off. `opts = { threshold = 0.7, radius = 3, only_3d = true }`: the brightness (luma, 0..1) where the glow starts, eased in over a soft knee so it has no hard edge, how far it spreads in DS pixels (0..8; 0 is off too), and whether only the 3D glows. With `only_3d` the glow skips 2D drawn over the 3D (such as white text boxes) and what's behind the 3D, using the renderer's depth, so it only works with the OpenGL renderer; on Compute and Software, and on the first frame after it's turned on, everything bright glows as with `only_3d = false`. `only_3d` must be a boolean. The bright parts are picked out and blurred at the DS's own resolution, so the glow costs the same at any internal resolution, then added to the screen at `strength`. Turning the glow off sets `only_3d` back to its default too.
- `melon.screen.vignette(strength[, opts])`: darkens the DS top screen towards its corners. `strength` is how dark the corners get, clamped to 0..1; 0 is off. `opts = { size = 0.6 }`: how far from the center the darkening starts, as a fraction of the distance to a corner (0..1), from where it deepens smoothly to the corners. With the WideMelon camera's margin it follows the top screen's middle 192 rows, as `tilt_shift`'s band does; with a wide top screen, its whole width (not the camera's window).
- `melon.screen.haze(strength[, opts])`: fades the far 3D of the DS top screen towards a pale color, the way HD-2D games fade their distance. Only with the OpenGL renderer, the one that hands out its depth; on Compute and Software it does nothing, and the first frame after it's turned on has no haze yet. `strength` is how far the farthest 3D goes towards the color, clamped to 0..1; 0 is off. `opts = { color = 0xDCE6F0, start = 0.9968, falloff = 0.0008 }`: the color as `0xRRGGBB` (a high byte is ignored, so an ARGB color works too; it must be a whole number), the depth where the haze starts, and how far past `start` it takes to reach full `strength`, eased in smoothly. `start` and `falloff` are clamped to 0..1 and are the renderer's raw depth, like `depth_of_field`'s, so they're tuned per game: the defaults suit Pokémon White's field, where the far end of a city street is hazed and the player and the roofs nearer the camera aren't. Only 3D pixels get the haze: 2D drawn over the 3D and what's behind the 3D stay as they are. Turning it off sets its options back to their defaults.
- Bloom, vignette and haze: each call sets only its own effect and keeps it until the script changes it, so a script can call any of them every frame and only a change sends an event. Non-number arguments and options raise errors like `tilt_shift`'s. Newest running script wins, for all three effects together, and a stopping or reloading script's go away with it (`ui/emulator/LuaBloomRequests.kt`, unit-tested). They're passes after the filter's own and the depth of field's, and before `tilt_shift`'s, so its blur softens the glow too (`VideoFilterPipeline.kt`: a bright pass and a two-pass blur at DS resolution, then one pass that adds the haze, the glow and the vignette, in that order; built on first use, skipped while off). They run on the finished frame, so without `only_3d` 2D such as white text boxes glows too, but never `melon.draw`. Without a glow the haze and the vignette are one pass that reads no glow, and a haze on its own with no depth to read draws nothing at all. Example: `docs/examples/lua/hd2d_white.lua`.
- `melon.screen.depth_of_field(strength[, opts])`: blurs the DS top screen's 3D by how far each pixel's real depth is from the focus, whichever way the screens are swapped. Only with the OpenGL renderer, the one that hands out its depth; on Compute and Software it does nothing. `strength` is clamped to 0..1, a fade of the whole effect; 0 is off. `opts = { radius = 4, focus_x = 128, focus_y = 96, focus_depth = nil, range = 0.0002, falloff = 0.0015 }`: the blur's radius at full strength in DS pixels (0..12; 0 is off too), and the focus point in DS pixels of the top screen's 256 x 192 view (`focus_x` -256..512, `focus_y` -192..384, so it can sit on WideMelon's wings and margins), whose depth is the focus; the default is the screen's center point. The focus follows a character standing at that point: the nearest 3D at and up to 18 DS pixels above it whose depth is the same 3 pixels lower, which is a quad facing the camera, as Pokémon White's characters are (floors, walls and roofs change depth from row to row). While something covers the character, so that only nearer 3D is at the point, the last focus holds, for up to about 8.5 s. With no such character, the focus is the nearest 3D at the point and the four points 3 DS pixels around it (or 6, if none of those is 3D). `focus_depth`, clamped to 0..1, sets the focus depth directly instead. Depths within `range` of the focus stay sharp, and the blur reaches its full radius `falloff` beyond that (both 0..1). Those three are in the renderer's raw depth (0..1), not in any game's units, so they're tuned per game: the defaults suit Pokémon White's field, where everything on screen is within about 0.002 of the player. 2D drawn over the 3D stays sharp. Like `bloom`, it's kept until the script changes it, so it's safe to call every frame and only a change sends an event; newest running script wins, and a stopping or reloading script's goes away with it (`ui/emulator/LuaDepthOfFieldRequests.kt`, unit-tested). The renderer only keeps the depth while a script's depth of field, haze, 3D-only glow, shading or sun shadows are on, so the first frame after it's turned on is still sharp.
- `melon.screen.shade(strength[, opts])`: soft contact shadows on the DS top screen's 3D, from its real depth: the base of walls, under roofs, around a character's feet, whichever way the screens are swapped. Only with the OpenGL renderer, the one that hands out its depth; on Compute and Software it does nothing, and the first frame after it's turned on is still unshaded. It's unsharp masking of the depth (Luft, Colditz and Deussen, 2006): where a pixel is farther than the blurred depth around it, it's in a corner or behind something, so it's tinted darker. `strength` is how far the most shaded pixels go towards the tint, clamped to 0..1; 0 is off. `opts = { radius = 8, range = 0.0008, color = 0x33384F }`: how far around a pixel the depth is blurred in DS pixels (1..16), how much farther than that blurred depth a pixel has to be to be fully shaded, in the renderer's raw depth like `depth_of_field`'s (0..1, so tuned per game: the defaults suit Pokémon White's field, where they shade the ground along walls, inside roof rims and around trees and the player softly, without dark outlines), and the tint the color is multiplied towards, as `0xRRGGBB` like `haze`'s (a high byte is ignored; it must be a whole number). Only 3D pixels are shaded: 2D drawn over the 3D and what's behind the 3D stay as they are. The depth is blurred at the DS's own resolution, so that costs the same at any internal resolution, and each pixel is compared with its own depth at full resolution, so the shading's edges stay as sharp as the 3D's. It runs after the filter's own passes and before the depth of field, which blurs it with the rest, and the bloom and haze come after it. Like `depth_of_field`, it's kept until the script changes it, so it's safe to call every frame and only a change sends an event; newest running script wins, and a stopping or reloading script's goes away with it (`ui/emulator/LuaShadeRequests.kt`, unit-tested). Turning it off sets its options back to their defaults. While it's on, the renderer keeps each frame's depth, as for the depth of field. Example: `docs/examples/lua/hd2d_white.lua`.
- `melon.screen.sun(strength[, opts])`: sun shadows on the DS top screen's 3D, cast in one direction from its real depth and the camera the game drew it with, whichever way the screens are swapped: roofs and walls throw long shadows across the ground, and walls facing away from the sun go dark. Only with the OpenGL renderer, the one that hands out its depth and camera; on Compute and Software it does nothing, and so it does for a scene with no usable camera (W-buffered or orthographic) and on the first frame after it's turned on. Each 3D pixel's position is rebuilt in the camera's view space and stepped towards the sun; where the depth on screen at a step is nearer than the step, something stands in the way and the pixel is in shadow. A step that lands on 2D, on nothing, off the screen, or on 3D the game drew under another camera (Pokémon White's characters) finds nothing there, so the characters don't cast through the steps, but they do darken where they stand in one. Since what's off screen can't cast a shadow, shadows fade out over the last 32 DS pixels before the edges the steps leave through rather than ending in a line. `strength` is how far shadowed pixels go towards the tint, clamped to 0..1; 0 is off. `opts = { direction = { 0.50, 0.83, 0.26 }, up = { 0.0006, 0.607, 0.794 }, length = 96, steps = 64, bias = 1, softness = 1.5, color = 0x33384F, near = 0 }`: the direction towards the sun in the camera's view space (x right, y up, z towards the viewer; a table of three numbers, normalized, not all 0), the world's up in the same space (for the characters' own shadows, below), how far the steps reach in view-space units (1..1024) in how many steps (1..128, whole), how much nearer the depth has to be than a step to count (0..64 units, which keeps surfaces from shadowing themselves), how far the shadow's edge is softened in DS pixels (0..8; under 1 is sharp), the tint, as `0xRRGGBB` like `haze`'s, and how far from the camera 3D has to be to cast at all, in view-space units (0..1024; 0, the default, lets everything cast), for what a game draws right in front of the camera over the scene, like Pokémon White's speech bubble tails (about 65 units away, where the town is 91 or more; the example uses 80). The units are the game's: the defaults suit Pokémon White's field, where a tile is 16 units, the tallest roofs are about 90 up and the sun comes from the north-east, 45 degrees up, so shadows fall down and left. The characters cast their own shadows through the renderer: it gets the newest script's `direction` and `up`, and draws each polygon the game drew under another camera that writes depth (White's characters, sprites turned to face the camera) a second time, stood upright on its feet (its texture's lowest row that shows, so a sprite with transparent rows below its feet still stands on them), turned about them until it holds `up` and flattened onto the ground away from the sun, in its texture's shape. Where that lands on the scene's depth, nearer things in front of it (the character itself too) hiding it, the pixels are shadowed as fully as the steps' shadows, so a character standing in a building's shadow doesn't darken it twice. The game's own translucent blob shadows write no depth, so they cast nothing. Only the frame's flags change: the picture and its depth are the same with or without it. Only 3D pixels are shadowed: 2D drawn over the 3D and what's behind the 3D stay as they are. The steps are taken at the DS's own resolution, so they cost the same at any internal resolution, and each pixel takes the shadow of the DS pixels around it that are on its own surface, so the shadows' edges stay as sharp as the 3D's. It runs after `shade` and before the depth of field, which blurs it with the rest. Like `shade`, it's kept until the script changes it, so it's safe to call every frame and only a change sends an event; newest running script wins, and a stopping or reloading script's goes away with it (`ui/emulator/LuaSunRequests.kt`, unit-tested). Turning it off sets its options back to their defaults. While it's on, the renderer keeps each frame's depth, as for the depth of field. Non-number arguments and options raise errors like `tilt_shift`'s. Example: `docs/examples/lua/hd2d_white.lua`.
- `melon.gpu.hide_textures(hashes)`: the OpenGL renderer leaves out every polygon whose texture is one of `hashes`, a table of up to 64 texture content hashes (whole numbers from 1 to `0xFFFFFFFF`, written in hex like `0xC9FDE257`); `nil` or `{}` hides nothing. Such polygons aren't drawn at all, as if the game hadn't sent them: no color, depth, edge marking, fog or sun shadow of theirs. The game itself sees no difference: its 3D state and 2D are untouched (only a game that captures its own 3D with display capture would capture it without them; nothing on the bottom screen changes in White's field), and Compute and Software draw everything. A texture's hash is its content as the DS reads it: the size, format and color 0 bits of its parameters, its texel bytes (for 4x4 compressed ones their slot 1 palette indices too) and, for paletted formats, the palette colors it can use, but not where it sits in VRAM or its repeat and flip bits, so it stays the same when the game loads it elsewhere, in another map or after a savestate load, and changes if its palette is animated. The desktop's `--list-textures` lists each frame's textures with their hashes, polygon counts and screen boxes, which is how to find one. The list is kept until the script changes it, so it's safe to call every frame; newest running script with a non-empty list wins, and a stopping or reloading script's goes away with it. Native only: the app isn't told. The renderer hashes each texture once and again only after its VRAM or palette changes, and only while some list or the desktop's listing is on. Non-table arguments, more than 64 hashes or a hash that isn't a whole number in range raise errors. Example: `docs/examples/lua/hd2d_white.lua` hides White's own blob shadows while its sun shadows are on.
- `melon.emu.fast_forward(bool)`.
- `melon.wide`, the WideMelon camera (see "Camera" under WideMelon). The window's x is its offset from the frame's center in DS pixels (positive is right), its y the same down the frame (positive is down, only ever non-zero with the camera's margin), and its zoom is its width over the layout's width (1 = native, more is zoomed out).
  - `camera()` → `x, zoom, y`, what's shown now (as of the last presented frame; `0, 1, 0` with the camera off). y comes last, so `local x, zoom = melon.wide.camera()` works.
  - `set_zoom(z)`: replaces the player's zoom, clamped to 1 up to the game's widest view; `set_zoom(nil)` hands it back, starting from where the script left it.
  - `pan(x[, y])`: replaces the player's pan, clamped to how far the window can go at its zoom; `pan(nil)` hands it back the same way. y is optional: left out or nil, the player keeps the vertical pan, so `pan(40)` sets only x and `pan(nil, 20)` only y.
  - `hold_native(bool)`: while true, the window stays at 1x in the middle (menus, text, battles); the player's zoom comes back after.
  - `set_zoom` and `pan` take a number or nil (`pan`'s y may also be left out), `hold_native` a boolean; anything else, NaN or no argument is an error. Requests last until changed, cost an event only when they change, and go away when the script stops or reloads. Each of zoom, pan x and pan y comes from the running script that changed its requests most recently among those asking for one, and 1x is held while any script holds it (`ui/emulator/LuaWideCameraRequests.kt`, unit-tested). They do nothing while the camera is off; the camera itself stays available in RetroAchievements hardcore, where Lua is off. A script reading the right stick for itself should call `pan(...)` too, or the stick also pans the camera. Example: `docs/examples/lua/wide_camera_test.lua`.
- `melon.options`: plain table built at each load, typed values (boolean, integer when integral, number, string); undeclared keys are nil.
- `melon.state.save(slot)` → true, or false plus an error; `load(slot)`; `has(slot)`. Slots 1–4 per script, in memory only (survive reset and option restarts, freed on switch-off, gone at session end, never touch the player's slots). One save per 30 frames per script; saves and loads cost 1M work steps; all script slots together are capped at 64 MB. `load` runs after every script's `on_frame`, backs up first like a player load, drops that frame's input override, resets the achievements display, and makes `on_state_loaded` run before the next `on_frame`. A queued load is dropped if the player loads or resets first. `Savestate` stays out of `LuaEngine` through a small callback interface in `MelonInstance`.
- `melon.storage`: `get(key)`, `set(key, value)` (nil deletes), `keys()`, `clear()`, `flush()`, `size()` → bytes used, limit. Keys are strings up to 256 bytes. Values: strings, numbers (integers and floats kept apart), booleans, tables (up to 16 deep, string or integer keys, no cycles); `set` deep-copies, `get` returns a fresh copy. 256 KB per script, encoded; going over is a catchable error. 1 work step per byte encoded or decoded.
- `require("lib.util")` loads `lib/util.lua` (`lib` → `lib/init.lua`; `x.lua` wins over `x/init.lua`). Text only, chunk name `=lib/util.lua`, called with name and path like stock Lua, cached per state, loops caught, 1 work step per source byte, errors keep their traceback. No `package` table. Top-level `.lua` files can't be required.
- Images: `melon.image.load("img/hud.png")` → image, or nil plus an error; `melon.image.new(w, h, argb_string)` (4 bytes per pixel, 0xAARRGGBB little-endian); `img:size()` → `w, h`.

### Drawing (`melon.draw`)

- `pixel(screen, x, y, color)`, `line(screen, x1, y1, x2, y2, color)`, `rect(screen, x, y, w, h, color[, filled])`, `circle(screen, cx, cy, r, color[, filled])`, `text(screen, x, y, str, color[, bg[, size]])` → width in DS pixels, `image(screen, x, y, img[, opts])` with `opts = { scale = 1, src = {x, y, w, h}, alpha = 1 }`.
- `screen` is `"top"` or `"bottom"` (the DS screen, so drawings follow swap). Coordinates are DS pixels (256×192); fractions land on the nearest half pixel (the overlay is 2×). Shapes are one DS pixel thick, off-screen parts are clipped. Rect outlines sit inside the rect; zero/negative size draws nothing; lines include both ends. A circle's center is a pixel corner like `rect`'s x/y; the outline is pixels whose center is between r−1 and r from the middle; r ≤ 0 draws nothing; radii capped at 2^28.
- Text: melonDS's OSD font (`melonDS-android-lib/src/frontend/qt_sdl/font.h`), lines 7 DS pixels apart, `\n` starts a line, non-ASCII draws `?` per code point, `size` 1–4, `bg` is one box around all lines.
- Image `scale` is a multiple of 0.5 from 0.5 to 8 (0.5 = one image pixel per overlay pixel), nearest neighbor; `src` outside the image is transparent.
- Colors are `0xAARRGGBB` masked to 32 bits (-1 = opaque white). `0xFF0000` has alpha 0 and draws nothing.
- Auto-clear: a frame shows only what `on_frame` and `on_frame_end` drew for it. Draws anywhere else do nothing. There's no `clear()`.
- Costs: 32 work steps per command plus 1 per clipped pixel at 2× (2 for images), plus 1 per byte of text; circles also 2 per visible row. Caps per script per frame: 4096 commands and 64 KB of text, across both callbacks. Fully off-screen draws aren't recorded or counted.
- The app's FPS counter sits over the top-left of the top screen.
- With the WideMelon camera on, the top screen's drawings follow the window: they stay on the frame's middle 256 columns and 192 rows wherever the window puts them, at the window's scale, cut to the picture when panned off its edge (sideways, or up and down into the margin).

### Folder content caps

Kotlin (`impl/LuaScriptFolderContent.kt`) walks the subfolders at launch when any script is on: at most 4 levels, 64 folders (root not counted), 4096 files found, one children query per folder. Path parts outside `[A-Za-z0-9_-]` are skipped (modules and images). Modules: 1 MB each, 2 MB and 256 files total. PNGs: each ≤ 1024×1024, at most 128 files and 4M pixels total, decoded unpremultiplied and sent as ARGB ints. Caps are taken in path order; once one file doesn't fit a total, later ones are left out too, and their names are sent so the error says why.

## Code facts

- **Draw path:** draw calls only record commands into a per-script list (text in a per-script string store, outside the Lua memory cap). `LuaEngine::endFrame()` runs `on_frame_end` and then rasterizes (`scripting/LuaDraw.{h,cpp}`) every running script's lists into the shared buffer in script order (later on top). A script that errors mid-frame shows nothing that frame. `endFrame()` runs whenever `runLuaFrame` ran, so a stopped script is still cleared. A drawn image is anchored in a per-frame registry table until rasterized.
- **Overlay texture:** one per `Frame` (`renderer/FrameQueue.{h,cpp}`), 512×772 (the frame layout at 2×, bottom screen from row 388), created lazily and zero-filled, uploaded on the emulator thread after `RunFrame` and before the frame's `renderFence`, so it can't lag the game image. Only rows with content now or last time are uploaded. `DSRenderer` draws it per screen with a passthrough premultiplied shader (filters never touch it), interleaved: under-screen, its overlay, over-screen, its overlay. With WideMelon it uses the screen's native rect, so it stays on the center 256 (with the camera, `ScreenDrawing.overlay`: that rect in the window, cut to the picture). `ExternalPresentation` draws it too.
- **Overlay in savestate/rewind pictures:** Settings → Display "Show script drawings in save state pictures", off by default, an atomic for the emulator thread. `ScreenshotRenderer` blends it with a 2×2 average (no swizzle: the textures share byte order there); the software path blends on the CPU.
- **Images:** folder PNGs are premultiplied by native and shared, immutable, for the session outside the Lua memory cap (`LuaFolderContent`). `new` images live in Lua's allocator and count. The image metatable is hidden from `getmetatable`.
- **Storage:** `scripting/LuaStorage.{h,cpp}`, a versioned binary codec; the key → encoded map lives in `LuaScript` (`LuaEngineInternal.h`), not the Lua state, so it survives reset and switch off/on. A corrupt blob starts empty (logged) and isn't overwritten until the script writes. Snapshots are encoded only when changed: on `flush()` (end of frame), every 600 frames, when the emulator thread parks for a pause, when a script stops, and at `stop()` after `on_unload`. They go into a global outbox (mutex, outside `MelonInstance`, since `stopEmulation` destroys the instance); an event wakes Kotlin to drain it on IO, and a final drain runs before `stopEmulator()` returns. A snapshot that can't be handed over JNI goes back into the outbox. `impl/LuaScriptDataStore.kt` writes `files/lua-data/<gameKey>/<script>.bin` (temp file + rename). Game key is the game code if it's 4 uppercase letters/digits and not `0000`, otherwise `homebrew-<first 16 hex digits of SHA-256 of the ROM URI>`; if the header can't be read, storage is session-only. An empty store deletes its file; a file over 256 KB is ignored. Not in savestates or rewind; not deleted when the script leaves the folder.
- **Host test:** `app/src/test/cpp/LuaStorageTest.cpp` tests the codec. Built by hand, not wired into Gradle (command under "Testing").
- Layout rebuilds (fold, rotation, swap, script layout switch) carry held touches over to the new controls, so a held button isn't released.

## WideMelon

**How it works.** A width W (even, 256..768; anything else counts as off, `WideMelon::SanitizeWidth`) is set on the GL or compute renderer, and `GPU3D` asks the renderer for it, so a fallback to 256 (W over `GL_MAX_TEXTURE_SIZE`, read once) can't leave geometry squeezed. Each vertex's clip-space X is squeezed by 256/W around the viewport center (`WideMelon::ProjectX`, rounded), so what the game would clip at the sides lands in the extra space; PosTest isn't squeezed. BoxTest tests the native box first and only retries a miss squeezed for a view 8 px wider than W, so a native hit never changes. Culling uses the X from before the squeeze, and the polygon pipeline's timing comes from the native view's clip result (`GPU3D::NativeClipVertices`), so the game sees stock geometry timing. The width is latched at the polygon RAM swap (or while geometry is off), and the targets resize at `RenderFrame`. Display capture and `GetLine` take only the center 256. The compositor outputs `W × scale` by `386 × scale`: the 3D screen's extra columns ("wings") show the 3D image (with `_3dxpos` scroll), the other screen sits centered with black bars. `GetOutputWidth()` is the compositor's width and can lag the requested one; the app sizes its frame texture from it every frame. Savestates don't store the width.

**Code:** core `WideMelon.h`, `GPU3D.*`, `GPU3D_OpenGL.*`, `GPU3D_Compute.*` and `GPU3D_Compute_shaders.h`, `GPU_OpenGL.*` (compositor, wing hold), `GPU_OpenGL_shaders.h`, `GPU2D_Soft.cpp` (per-line flags), `GPU.cpp`. App: width through `EmulatorConfiguration` → JNI → `Configuration.h` → `MelonInstance` (kept there and re-applied on every `updateRenderer()`, which can build a fresh renderer); `Frame` carries `topWidth` to Kotlin; `DSRenderer.kt` (UVs, top rect via `getTopScreenDrawRect`); `VideoFilterPipeline.kt` and `ShaderProgramSource.kt` (filters clamp horizontally only when needed and use a logical width); `ScreenshotRenderer` crops to 256×384 so savestate/rewind pictures are unchanged. Width is applied on OpenGL and Compute; Software uses 256.

**Wings rule, per line.** The 2D line renderer writes flags into the line's control word (`dst[256*3]` in `GPU2D_Soft.cpp`) from the same snapshot it draws the line from, so mid-frame changes and threaded 2D are handled and the wings follow unit A to either screen: bit 18 = 3D in the wings, bit 21 = white wings (screen off or forced blank), bit 22 = unit A drew 3D on BG0 this line, whatever the windows do (only used by the wing hold). Master brightness leaves bits 5–13 free; 8–12 and 19–20 are unused.

**Wing planes.** On a line with bit 18, `SoftRenderer::DrawWingPlanes` also stores planes 0–2 for one wing pixel per side. If the edge column (0 for the left wing, 255 for the right) has the 3D on top with only the backdrop under it, the wing gets that column's planes and `WingPixel()` composites them with the wing's 3D pixel through `CompositePixel`, as the edge pixel would be: blended with or faded over the backdrop, with the edge's compmode and window effects. The wing's transparent 3D shows the backdrop only where the edge visibly does too: if the 3D one native pixel in from the edge (column 1 or 254, with the X scroll, at any scale) isn't transparent, a transparent wing 3D pixel is taken as opaque (alpha 31 for compmode 4, 1 for 0, 2 and 3), so it shows the 3D clear color. That's for a squeezed screen-wide 3D quad (Contra 4's "Licensed by Nintendo" screen and its fades), which leaves the wings' 3D transparent while the edge's isn't; the CPU never sees 3D alpha. It's one pixel in because squeezed geometry ending at the screen edge can miss column 255 (that screen shows a 1-px white line there). On lines where a 2D layer is over or under the 3D at the edge, the planes carry `GPU2D::WingRaw3D` and the wing shows the 3D as it is, transparent or not, with the BLDCNT fade for BG0 as first target. The planes sit after each screen's 192 lines in its framebuffer (`GPU2D::AccelWingPlanesStart`), so they swap with POWCNT and always belong to the frame being composited, also with threaded 2D and the Blit after the readback. The compositor uploads them as `WingPlanesTex` (6×384 `RGBA8UI`, unit 10). Lines without bit 18 are unchanged (black, white or held).

**Windows.** With wide view on, native columns 0 and 255 take their neighbor's window mask, which removes a 1-px backdrop seam (also in capture). With any window on, a line gets 3D wings only if BG0 shows at column 0 or 255 (WINOUT and the OBJ window included), so a window letterbox blacks the wings out with the middle. One wings bit per line: BG0 at one edge gives 3D on both sides. A window cutting BG0 mid-line doesn't affect the wings. A wing that carries on its edge column follows that column's window effects; one that shows the 3D as it is ignores the window's effect-enable bit.

**Dual-screen wing hold.** Games with 3D on both screens (Phantom Hourglass, Mario Kart DS) move unit A every frame, so each screen's wings would flash at 30 Hz. The GL compositor keeps a copy of the output's wing columns (`HeldWingsTex`, blitted after drawing while both halves have had 3D lately). When unit A's wings appear in the other half, a half that had its own in the last 2 frames reuses them, only on lines that had bit 18 in the copy and would be black now, for at most 2 frames in a row; a width or scale change drops the copy. The half unit A is in comes from bit 22, so a window blacking out all of unit A's wings doesn't stop the hold. Single-screen 3D games never copy or hold.

**Adreno gotcha:** held lines reach the shader as bit 13 of the line's control word (`GLCompositor::PrepareWingHold`), because Adreno never applied an earlier `uvec4 uWingHold[3]` mask to word 0, which gave flickering black notches on Phantom Hourglass's top screen; keep the flag in the control word.

**Lesson:** for wing bugs, a per-line dump on the phone (output, held texture, 3D texture and each line's control bits) found what code reasoning didn't, so write a new one rather than guess (the old one is gone).

**Known limits:** edge pop-in in games that cull on the CPU or with PosTest; ortho 3D HUDs and full-screen 3D quads stay 256 wide; 2D-only scenes get black wings; transparent 3D shows the backdrop in the wings only where the edge visibly does ("Wing planes"), otherwise the 3D clear color; BoxTest makes it visible to the game; loading a state made at another width gives a frame or two of squeezed geometry.

**Polygon RAM** (`GPU::WidePolys`, debug switch `widepolys`, on by default): the wide view keeps polygons the native view would clip, so it would hit the DS's 2048-polygon limit early and drop polygons the DS draws. With the switch on the game sees the native view's polygon and vertex counts, limit and DISP3DCNT bit 13, and the scene is stored in a list twice the DS's size, half of it for wing-only polygons. Details and the savestate format in [docs/plan-widemelon-polylist.md](docs/plan-widemelon-polylist.md).

**Compute renderer.** Same width rules, latch and `WideXAdjust` as GL. Its work buffers and shaders are built for the width (`ScreenWidth` etc. are shader constants), so a change of the output width recompiles all 33 shaders inside `RenderFrame`, a short pause on fold or rotation. The dispatches need whole coarse tiles (`ScreenWidth/CoarseTileW`) and whole bin-mask clear groups, so the internal width is rounded up until both divide (256 always does); geometry sits at the left, the final pass doesn't store the extra columns on the right, and the 3D texture is exactly W × scale. The final pass writes only the center 256 to the low-res image that capture and `GetLine` read. At 256 the shaders get no extra defines, so they're unchanged.

### Camera

Display-side only: the game's camera never moves (design and phone results in [docs/plan-widemelon.md](docs/plan-widemelon.md), "Camera: pan and zoom"). Mods tab, under widescreen: Camera (off by default), "Zoom out up to" (426, 448, 512, 640 or 768 DS pixels, 512 by default), "Return to center when moving" (on by default) and "Auto zoom in on text" (on by default, see "Pokemon game state" below), stored as `RomModsConfig.wideCamera`, `wideCameraMaxWidth`, `wideCameraReturnToCenter` and `wideCameraZoomOnText` (new keys, so older configs read as off, and the last as on). The last three only show with the camera on. The last zoom picked with the Camera Zoom hotkey is kept per game too (`wideCameraZoom`, written from the emulator through `EmulatorViewModel.onWideCameraZoomPicked` into the ROM that camera session launched), and the camera starts there the next time it comes on. The view model's `WideCameraState` carries a session number, the settings and the start zoom apart from the settings, so a pick never counts as a settings change (which drops held input), a recreated activity's controller starts at the latest pick, a pick still on its way during a ROM switch is dropped, and a new session resets the controller even if the off state between sessions was conflated away; auto-1x and script holds override it on screen without changing it, and pinches and scripts' zooms aren't kept.

- **Two widths.** The layout keeps its show width Wd; the core renders at Wr, which follows the zoom the player picked, not the max zoom-out (`WidescreenLaunch.getRenderWidth(showWidth, zoom)`, sent where the width always went, with the margin rows from the same Wr). The picked zoom is the camera's target zoom: the hotkey, a pinch, the remembered start zoom and a script's zoom. It's rounded up to the next 0.25 step and kept between Wd and the max zoom-out (`getMaxRenderWidth`), so at 1x the camera costs nothing. The automatic pull-ins (text, battle, menus, fades, swapped screens, `hold_native`, the no-wing-lines snap) only change the shown zoom, so they never resize the core. The controller asks the view model for a width through `onRenderZoomNeeded` (`EmulatorViewModel.onWideCameraRenderZoomNeeded`, stale sessions dropped): wider at once, narrower only with no finger down, after the shown zoom has eased in, and after 6 frames in a row, so a pinch or a script's wobbling zoom doesn't recompile Compute's shaders every frame. The zoom range comes from the max zoom-out, not the frame; while a wider frame is on its way, the shown zoom is held to the frame's width. Camera off, or a variant that isn't wide: Wr = Wd and nothing changes. A max zoom-out no wider than Wd counts as the camera off for that variant (no room to zoom or pan), and the Mods tab only offers widths past the shown one, with a note when the stored one isn't. The core only adds `OutputLayout::TopWingLines`: the top screen's lines with 3D wings, counted in `GLCompositor::PrepareWingHold` from control word bit 18 plus the lines the wing hold fills (`WingHoldLines`, which are only ever black lines), carried per `Frame` to Kotlin with the frame.
- **The window.** `WideCameraController` moves `domain/model/camera/WideCamera` (unit-tested, no Android) once per presented frame on the render thread (`FrameRenderCoordinator`), so every surface shows the same `WideWindow` [x, x + w) of the Wr-wide top half. `getScreensDrawing` shapes the screen's rect for Wd, maps the window across it and letterboxes it top and bottom when w > Wd. When only the window moved, `DSRenderer` refills its quads into a reused buffer (`glBufferSubData` into storage made once) and rebuilds the shadows only if a drawn rect changed; the camera reuses its input and its window at rest, so a moving camera allocates its new window and the drawing's few small objects per frame. The bottom screen and touch are unchanged.
- **Controls.** Right stick X pans (dead zone 0.2, 300 DS px/s, eased), unless the right stick (`AXIS_Z`/`AXIS_RZ`) is mapped to an input, and only from a device whose `AXIS_Z` and `AXIS_RZ` are a centered pair that has been seen resting in the middle (`CameraStickReader`, so a trigger on `AXIS_Z` never pans). Not while a menu or dialog is over the game; opening one drops the held stick, D-pad and touch. Camera Zoom is one mappable hotkey (Input setup), the right stick's click (`KEYCODE_BUTTON_THUMBR`) by default, like PokeDaisy's Expand: each press goes to the next step, in steps of 0.25 with the widest view as its own last step, and from the widest back to 1x (1, 1.25, 1.5, 1 with a 1.5 widest view; `WideCamera.cycleZoom`). After a pinch, a press goes to the step above. Holding it doesn't repeat (`InputProcessor` drops the key's repeats, also the first one after a menu closes with the key still held). Presses during auto-1x still count and show once it ends, and a press before the first wide frame (at launch, or with a width change on its way) waits for it; presses while the camera is off, or while a script sets the zoom, are dropped. Stored controller configs keep their mapping: an entry for an input this version doesn't know (such as `CAMERA_ZOOM_IN` and `CAMERA_ZOOM_OUT` from test builds) is dropped on load instead of failing the whole file (`InputConfigDto.input` is the name as text), and a config with no Camera Zoom entry gets R3 unless R3 is already mapped to something (`withDefaultCameraZoomKey`, used on load and by the v33 migration, which would otherwise write the hotkey as unmapped; unit-tested). Nothing else in the defaults uses R3. One finger dragging the DS top screen pans, two pinch, and the picture moves 1:1 with the finger (the drag is measured against the drawn picture's width). That's only while the top screen is the wide one (not swapped) and its rect doesn't overlap the touch screen's, since a top screen stacked over the touch screen would take the game's touches; such layouts have the stick and hotkeys only. A listener change mid-gesture drops the touch. With the stick idle and the D-pad or left stick held, the pan eases back to the middle if return to center is on.
- **Lua and the right stick.** A script that reads `melon.input.stick("right")` for its own use (aiming, say) also pans the camera; it should take the pan over with `melon.wide.pan(...)` (`pan(0)` keeps the middle) while it uses the stick.
- **Back to 1x.** Straight to 1x in the middle when the frame has no top-screen wing lines, with the screens swapped (the wide screen is then the touch screen), or while a script holds native. Dual-screen 3D games (Mario Kart DS, Phantom Hourglass) aren't held: their held lines count as wings, and the held wings cover the whole render width. The player's zoom comes back (eased, pan centered) once the frame has been free of those for 0.25 s. In the Pokemon games below, the scene replaces the wing-line rule; swapped screens and `hold_native` still force 1x at once in every game.
- **Pokemon game state** (PokeDaisy's auto zoom, [docs/plan-expand-parity.md](docs/plan-expand-parity.md) Phase 1). For the carts PokeDaisy's field read knows (Platinum US rev 1 and French, HG/SS US, German and French, Black/White US/Europe and French, Black 2/White 2 US/Europe, the other language ports in `pk_nds_ports_gen.h`, and Origin HeartGold; plus two carts of our own, US Platinum rev 0 and Diamond ADAE rev 5 and 13, see `GameState::findGame`), the camera follows the game's scene instead of the wing lines:

  - **Camera** (`WideCamera.updateForScene`, PokeDaisy's `WideCamera.frame`). BATTLE, MENU and OFF always pull in to 1x, TEXT only with "Auto zoom in on text", FIELD never, and FADE decides nothing (the zoom holds through a door's fade, and stays in through a menu's closing fade).   - **Gen 4 wide battles** (PokeDaisy's battle margins, [docs/plan-expand-parity.md](docs/plan-expand-parity.md) Phase 3). - **Lua:** `melon.wide` above; `melon.wide.camera()` reads atomics the controller sets through `MelonEmulator.updateWideCamera`, on the first presented frame of each controller (so a recreated activity never leaves the old values) and whenever the window moves.

  - **Frame layout.** The top screen's half of the frame texture is Hr = 192 + 2M rows, then the 2 gap rows, then the bottom screen's 192; DS line y of the top screen is row y + M, and M = 0 is the old 386 row layout. `MelonInstance` sizes the frame from `GetOutputWidth()` and `GetOutputMargin()` (the latest output frame's, which lag the requested ones together), and Software is always M = 0. Screenshots and savestate pictures still crop to the native 256×384, skipping the margin (`ScreenshotRenderer`). The Lua overlay texture keeps the old layout.
  - **The window** gets a y and a height (`WideWindow.frameHeight`, `y`, `height`, `offsetY`): h = 192 · zoom clamped to Hr, letterboxed only by what Hr can't cover (`getScreensDrawing`), and the vertical pan is clamped to (Hr − h)/2 and eases back to the middle like x. Without a window the top screen shows rows M..M+191 (`ScreenDrawing.topRow`/`bottomRow`), and at 1x the window is those rows with the same rects, so the output cap (`nativeRectAt1x`) is unchanged. The bottom screen never has a margin, so swapped it shows all its rows.
  - **Controls.** The right stick's Y (`AXIS_RZ`, down is down) pans vertically with the same dead zone and speed, and a drag's Y moves the picture with the finger (measured against the drawn picture's height). Return to center needs both stick axes idle.
  - **Core.** `WideMelon::ProjectY` squeezes clip-space Y by 192/Hr next to the X squeeze, and HiresPosition stretches it back around the viewport's center plus M. The native-view logic (culling, `NativeClipVertices`, widepolys' counts, the BoxTest retry) keeps native Y, so the game still sees its native view; FinalPosition Y stays the squeezed native frame, so the 8-bit field, the sort key and Degenerate are unchanged. HalfCamera's shadow state carries native Y, and the `GP3W` savestate block native Y and M. OpenGL has a `WideYAdjust` like `WideXAdjust`, offsets the clear bitmap and the shadow-mask scissor by M, and capture, `GetLine` and `Hash3D` read rows M..M+191; Compute rounds its internal height up to whole coarse tiles, passes the scale to the shaders instead of deriving it from height/192, and guards stores to the real height. Margin rows have no 2D line, so each margin pixel is drawn as a wing pixel of the nearest edge line (0 above, 191 below): 3D with that line's fade and brightness when it has 3D wings, black or white like its wings otherwise; 2D on the edge line (a HUD) isn't repeated. The wing hold's copy keeps the margin rows, held on the frames their edge line is. `GPU::Comp1x` is off while M > 0. M = 0 is bit-exact with the camera off; at 1x with M > 0 the 3D goes through the squeeze, so it can differ by sub-pixel rounding.

### Wide layouts

The player places the wide top screen in the normal layout editor. Each layout variant (`UILayout`: folded/unfolded, portrait/landscape, displays) has its own `wideAspect: WidescreenAspect?` (null = normal 4:3 at 256). `WidescreenAspect` has stable keys 16:10, 16:9, 20:9, 21:9 → widths 308, 342, 426, 448 (`192 × ratio`, rounded to even). A layout is "wide" when any saved variant has a ratio. Old layout-level `wideAspect` values are copied to the saved variants on load.

- Editor: the top screen's Wide chip sets and re-shapes only the variant being edited (same rule as automatic placement); its aspect lock offers the variant's ratio next to 4:3, 16:9 and Free. Lists show "Wide 20:9", or "Wide" when variants differ.
- Mods tab with widescreen on: "Wide layout" is Automatic or a layout marked wide (`LayoutSelectorActivity`, wide-only filter). Automatic uses the tab's own ratio (16:9 default) with automatic widening; with a wide layout the ratio is "set by the layout". The row says it needs OpenGL or Compute when the global renderer is Software.
- Launch: widescreen on + wide layout found + OpenGL or Compute → that layout (`EmulatorViewModel.startObservingLayoutForRom`, `wideLayoutId ?: layoutId`). No wide layout found → normal layout with automatic widening. Widescreen off or Software → 256 for the session. Lua `set_layout` and player picks still override.
- During play the width follows the active variant: on fold, unfold or rotation Kotlin sends the new width, applied on the emulator thread through `SetViewWidth` on the GL or compute renderer (no rebuild); a frame or two shows the old width in the new rect.
- Top rect: a rect at least as wide as the frame (2 px tolerance) is used as drawn, frame centered at its exact aspect. Otherwise it's widened around its center up to the surface edge without covering the bottom screen's rect, then shrunk to fit; a bottom screen sharing rows with the top stops the widening at its near edge. An unedited variant (from the default 4:3 layout) still gets automatic widening. Touch is untouched.

## Testing

`LuaStorageTest.cpp` builds with any C++17 compiler, for example from `app/` with MSYS2's MinGW, in an empty folder of your choice:

```
gcc -c -O1 -Isrc/main/cpp/lua $(ls src/main/cpp/lua/l*.c | grep -v -e /lua.c -e /luac.c -e /lstrlib.c) src/main/cpp/lua/patched/lstrlib.c
g++ -std=c++17 -O1 -Isrc/main/cpp/lua -Isrc/main/cpp src/test/cpp/LuaStorageTest.cpp src/main/cpp/scripting/LuaStorage.cpp *.o -o lua-storage-test
./lua-storage-test
```

The Android emulator has no GLES 3.2, so there it can only check the Mods tab and layout UI. WideMelon output needs the desktop build (`--wide W`, `--wide-margin M`) or a phone. Not phone-tested yet: the wings' window handling, and script drawings in savestate pictures.
