# Per-game mods (WideMelon + Lua)

Two mods, both set per game in ROM details → Mods tab and stored in `RomConfig.mods` (`RomModsConfig`): **WideMelon** widens the 3D view, and **Lua scripts** can read and change input and memory, draw on the screens and control a few emulator settings. Nothing runs unless it's switched on for that game. Paths below are under `app/src/main/` unless they start with `melonDS-android-lib/`; the core submodule has its own repo.

## Decisions to keep

- **Our own Lua API, no compatibility.** MelonMix (KHMelonMix's per-game C++ plugins) and DraStic script compatibility are dropped. DraStic's own Lua API readme (section 8) is a design reference only; DraStic is closed source, so there's no repo to point at. Old DraStic scripts get ported by hand.
- **RetroAchievements hardcore:** Lua is fully off, read-only scripts included (RA bans scripting outright). It's gated next to cheats (`impl/emulator/EmulatorSession.kt`), the Mods tab disables the switches and says why, and `melon.state.load` checks hardcore again anyway. WideMelon stays allowed: RA exempts widescreen hacks. Its game-visible effects are that BoxTest is squeezed too and polygon RAM fills up sooner (see "Known limits" under WideMelon).
- **One linked SAF folder per game**, picked in the Mods tab (`OpenDocumentTree`, persisted read permission), not copied. Top-level `.lua` files are the scripts; subfolders hold modules and images. New scripts start switched off. The app never writes to or deletes from the folder.
- Lua 5.4.9 from lua.org under `cpp/lua/`, unchanged except `cpp/lua/patched/lstrlib.c` (a work budget in pattern matching and plain find). `cpp/lua/LICENSE` says how to redo the patch on an upgrade.
- WideMelon is from pruefsumme's `melonDS-android-lib` `widemelon` branch, GPL-3.0-or-later, reworked (per-line wings rule, one width source, off-center viewports). It works on the OpenGL and Compute renderers; Software stays at 256 (see [docs/shelved/widemelon-software.md](docs/shelved/widemelon-software.md)).

## Script folder and the Mods tab

- `LuaScriptFolderSync` keeps `luaScripts` (file name, switch, options) in step with the folder: top-level `.lua` only, sorted by name. It runs when the Mods tab shows, when ROM details resumes, and at game start. A gone file's entry is dropped. If the folder can't be read (not a directory, provider throws, cursor still loading or errored, permission lost) the list is kept and the tab offers to pick the folder again.
- Changing or removing the folder clears the list and releases the permission, unless another ROM or one of the app's own folders (ROMs, BIOS, saves, perf log) uses the same tree. Picking the same folder again keeps the switches.
- At game start only switched-on scripts that exist are read (1 MB cap each) and sent to native with their options, storage blob, modules and images (`LuaScriptSetup` array over JNI). Native never opens script files. Edits take effect at the next game start.
- Header (`impl/LuaScriptHeaderParser.kt`, reads at most 8 KB of the leading comment block): `-- description: ...` is shown under the name (otherwise the block's first comment line). Options:
  ```
  -- option: speed type=number min=1 max=10 step=1 default=5 label="Aim speed"
  -- option: hud type=toggle default=true label="Show HUD"
  -- option: mode type=choice values=easy,normal,hard default=normal label="Difficulty"
  -- option: map_layout type=layout label="Layout while the map is open"
  ```
  At most 16 options; key `[a-z_][a-z0-9_]{0,31}`; label up to 60 chars; choice up to 8 values of up to 24 chars; numbers finite, min < max, at most 1000 steps. `step` defaults to 1; `default` to min, false or the first choice; an off-step default snaps to the nearest step. Unknown attributes or bad lines make the line unreadable, and the tab says how many were skipped. Layout options have no default and store a layout UUID ("Don't change" = none). Stored values are `RomLuaScript.options: Map<String, String>`; a missing or invalid value falls back to the default.
- Pause menu → Mods lists every script loaded this session with its description, error or "Switched off", plus scripts that couldn't be read (with the reason, can't be switched on). Switching off/on is for this session only and never changes the ROM config; on means a fresh state and `on_load`. "Options…" saves to the ROM config and restarts the script with the new values (its savestate slots are kept).
- Saved data: the Mods tab shows "Saved data: N KB" with Clear (ignored for the running game).

## Lua runtime

- `cpp/scripting/LuaEngine.{h,cpp}`, owned by `MelonInstance`, emulator thread only. One Lua state per script, 32 MB each. The engine file keeps the lifecycle and `setupScript`; the sandbox is `LuaSandbox.cpp` and each part of the module has its own file (`LuaMemoryApi`, `LuaDrawApi`, `LuaFolderApi` for `require` and images, `LuaStateApi`, `LuaStorageApi`), sharing the per-script state through the private `LuaEngineInternal.h`.
- Sandbox: only `base`, `table`, `string`, `math`, `utf8`. No `io`, `os`, `package`, `debug`, `dofile`, `loadfile`, `warn`; `load` takes text only; `print` goes to the log; `setmetatable` refuses `__gc`; `collectgarbage` only takes collect/count/step/isrunning; `string.rep` and `table.move/insert/remove/sort` have size caps.
- Limits per call: 1M instructions (10M for the main chunk plus `on_load`), and a work budget of 20 steps per instruction charged by pattern matching, table functions, allocation, drawing, storage and `require`. Once either runs out, everything left in that call fails, so `pcall` can't keep a script alive. An error or a limit switches the script off for the session and shows a message. The goal is that a buggy script can't freeze the game, not defense against a hostile one.
- When a script stops, the swap, controls, fast-forward and layout it set go back to the player's values (`ui/emulator/LuaUiOverrides.kt`, unit-tested). Newest request from a running script wins; a change the player makes by hand clears the requests and becomes the baseline. Fast-forward's baseline is off at each session start. Only a real player layout pick clears layout requests.
- Reset reloads every running script (`on_unload`, fresh state, main chunk, `on_load`); switched-off scripts stay off. Sticks are forwarded to native only while a script is active and zeroed when the last one stops.
- Events to Kotlin go through the native event pipe (one write, at most 512 bytes of data) and carry the script's index. Screen and fast-forward requests are coalesced per call; Kotlin applies them only when they differ from the UI's state.

### Callbacks

| Callback | When |
|---|---|
| `on_load(game_code)` | End of `MelonInstance::start()`, after the main chunk |
| `on_frame()` | Just before `nds->RunFrame()`. Input changes apply to this frame |
| `on_frame_end()` | After `RunFrame` (and the software upload), before the overlay upload. Own instruction budget; `melon.frame()` is the frame that just ran; `press`/`release` apply to the next frame |
| `on_state_loaded()` | On the emulator thread before the next frame after a savestate or rewind load (those run on IO/UI threads and only set a flag), or a script load |
| `on_unload()` | `stop()`, reset, switch-off; then the state is closed |

### API (`melon`)

- `melon.game.code()`, `melon.game.title()`, `melon.frame()`, `melon.log(...)` (logcat tag `melonade-lua`, only while the debug log is on; script errors are always logged).
- Input: `melon.input.held()`, `press(mask)`, `release(mask)` (last one frame), `touch()` → `x, y, down`, `set_touch(x, y)` (held until `clear_touch()`), `clear_touch()`, `stick("left"|"right")` → `x, y`. Final mask each frame is `(user & ~release) | press`; the UI's own `pressKey`/`releaseKey` are untouched.
- `melon.KEY.*` are ready-made masks, not bit numbers (`melon.KEY.R` is 256, so use it as is, not `1 << melon.KEY.R`). Pressed = bit set. Bits: A=0, B=1, SELECT=2, START=3, RIGHT=4, LEFT=5, UP=6, DOWN=7, R=8, L=9, X=10, Y=11, TOUCH=12. The engine flips it to the core's active-low mask.
- Memory: `melon.mem.read8/16/32(addr)`, `read_s8/s16/s32`, `write8/16/32(addr, v)`, and `melon.mem.arm7.*` with the same names. Goes through the NDS bus (JIT-safe, like AR cheats). ARM9 checks ITCM/DTCM first (ITCM writes invalidate the JIT). Reads in 0x04xxxxxx raise an error on both CPUs (I/O reads have side effects).
- `melon.screen.swap(bool)`, `show_controls(bool)`, `set_layout(key)`: `key` names a `type=layout` option; Kotlin resolves its UUID. `set_layout(nil)` goes back to the player's layout. A key that isn't a layout option is an error; "Don't change" or a deleted layout does nothing. Scripts see layout options in `melon.options` as a boolean (picked or not).
- `melon.screen.tilt_shift(top, bottom[, opts])`: blurs the DS top screen above and below a sharp band, whichever way the screens are swapped. `top` and `bottom` are that side's strength, clamped to 0..1; `(0, 0)` is off unless `color` is above 0 with a `saturation` or `contrast` other than 1. `opts = { center = 0.5, width = 0.3, radius = 6, saturation = 1, contrast = 1, color = nil }`: the band's center and height as fractions of the screen's height (0..1), the blur's radius at full strength at the screen's edge in DS pixels (0..12), and color multipliers (0..2, 1 is no change) for the whole DS top screen, sharp band included. `color`, clamped to 0..1, is how strongly those multipliers apply, whatever `top` and `bottom` are, so `tilt_shift(0, 0, { saturation = 1.3, color = 1 })` is only the color boost; absent, the boost follows the blur: the multipliers are scaled by `max(top, bottom)` so they fade with it. The same `color` gives the same picture with or without a blur. Safe to call every frame, since only a change sends an event. Newest running script wins, and a stopping script's blur goes away with it (`ui/emulator/LuaTiltShiftRequests.kt`, unit-tested). It's two passes after the filter's own (`VideoFilterPipeline.kt`, built on first use, skipped while off, the player's filter setting untouched) that run on the finished frame, so they blur 2D such as text too, but not `melon.draw`. With no blur to draw only the color boost runs, as one pass of one sample per texel, built on its own first use. Examples: `docs/examples/lua/tilt_shift_test.lua`, `docs/examples/lua/tilt_shift_platinum.lua`, `docs/examples/lua/tilt_shift_white2.lua` (in the last two the color strength follows the Blur strength option, so strength 0 means no boost; otherwise it stays on when the blur clears, in every game state, and only hold L, tap R fades it off).
- `melon.emu.fast_forward(bool)`.
- `melon.wide`, the WideMelon camera (see "Camera" under WideMelon). The window's x is its offset from the frame's center in DS pixels (positive is right), its y the same down the frame (positive is down, only ever non-zero with the camera's margin, stage 2), and its zoom is its width over the layout's width (1 = native, more is zoomed out).
  - `camera()` → `x, zoom, y`, what's shown now (as of the last presented frame; `0, 1, 0` with the camera off). y comes last, so stage 1's `local x, zoom = melon.wide.camera()` still works.
  - `set_zoom(z)`: replaces the player's zoom, clamped to 1 up to the game's widest view; `set_zoom(nil)` hands it back, starting from where the script left it.
  - `pan(x[, y])`: replaces the player's pan, clamped to how far the window can go at its zoom; `pan(nil)` hands it back the same way. y is optional: left out or nil, the player keeps the vertical pan, so `pan(40)` sets only x and `pan(nil, 20)` only y.
  - `hold_native(bool)`: while true, the window stays at 1x in the middle (menus, text, battles); the player's zoom comes back after.
  - `set_zoom` and `pan` take a number or nil (`pan`'s y may also be left out), `hold_native` a boolean; anything else, NaN or no argument is an error. Requests last until changed, cost an event only when they change, and go away when the script stops or reloads. Each of zoom, pan x and pan y comes from the running script that changed its requests most recently among those asking for one, and 1x is held while any script holds it (`ui/emulator/LuaWideCameraRequests.kt`, unit-tested). They do nothing while the camera is off; the camera itself stays available in RetroAchievements hardcore, where Lua is off. A script reading the right stick for itself should call `pan(...)` too, or the stick also pans the camera. Example: `docs/examples/lua/wide_camera_test.lua`.
- `melon.options`: plain table built at each load, typed values (boolean, integer when integral, number, string); undeclared keys are nil.
- `melon.state.save(slot)` → true, or false plus an error; `load(slot)`; `has(slot)`. Slots 1–4 per script, in memory only (survive reset and option restarts, freed on switch-off, gone at session end, never touch the player's slots). One save per 30 frames per script; saves and loads cost 1M work steps; all script slots together are capped at 64 MB. `load` runs after every script's `on_frame`, backs up first like a player load, drops that frame's input override, resets the achievements display, and makes `on_state_loaded` run before the next `on_frame`. A queued load is dropped if the player loads or resets first. `Savestate` stays out of `LuaEngine` through a small callback interface in `MelonInstance`.
- `melon.storage`: `get(key)`, `set(key, value)` (nil deletes), `keys()`, `clear()`, `flush()`, `size()` → bytes used, limit. Keys are strings up to 256 bytes. Values: strings, numbers (integers and floats kept apart), booleans, tables (up to 16 deep, string or integer keys, no cycles); `set` deep-copies, `get` returns a fresh copy. 256 KB per script, encoded; going over is a catchable error. 1 work step per byte encoded or decoded.
- `require("lib.util")` loads `lib/util.lua` (`lib` → `lib/init.lua`; `x.lua` wins over `x/init.lua`). Text only, chunk name `=lib/util.lua`, called with name and path like stock Lua, cached per state, loops caught, 1 work step per source byte, errors keep their traceback. No `package` table. Top-level `.lua` files can't be required.
- Images: `melon.image.load("img/hud.png")` → image, or nil plus an error; `melon.image.new(w, h, argb_string)` (4 bytes per pixel, 0xAARRGGBB little-endian); `img:size()` → `w, h`.

### Drawing (`melon.draw`)

- `pixel(screen, x, y, color)`, `line(screen, x1, y1, x2, y2, color)`, `rect(screen, x, y, w, h, color[, filled])`, `circle(screen, cx, cy, r, color[, filled])`, `text(screen, x, y, str, color[, bg[, size]])` → width in DS pixels, `image(screen, x, y, img[, opts])` with `opts = { scale = 1, src = {x, y, w, h}, alpha = 1 }`.
- `screen` is `"top"` or `"bottom"` (the DS screen, so drawings follow swap). Coordinates are DS pixels (256×192); fractions land on the nearest half pixel (the overlay is 2×). Shapes are one DS pixel thick, off-screen parts are clipped. Rect outlines sit inside the rect; zero/negative size draws nothing; lines include both ends. A circle's center is a pixel corner like `rect`'s x/y; the outline is pixels whose center is between r−1 and r from the middle; r ≤ 0 draws nothing; radii capped at 2^28.
- Text: melonDS's OSD font (`melonDS-android-lib/src/frontend/qt_sdl/font.h`), lines 7 DS pixels apart, `\n` starts a line, non-ASCII draws `?` per code point, `size` 1–4, `bg` is one box around all lines.
- Image `scale` is a multiple of 0.5 from 0.5 to 8 (0.5 = one image pixel per overlay pixel), nearest neighbor; `src` outside the image is transparent.
- Colors are `0xAARRGGBB` masked to 32 bits (-1 = opaque white). `0xFF0000` has alpha 0 and draws nothing.
- Auto-clear: a frame shows only what `on_frame` and `on_frame_end` drew for it. Draws anywhere else do nothing. There's no `clear()`.
- Costs: 32 work steps per command plus 1 per clipped pixel at 2× (2 for images), plus 1 per byte of text; circles also 2 per visible row. Caps per script per frame: 4096 commands and 64 KB of text, across both callbacks. Fully off-screen draws aren't recorded or counted.
- The app's FPS counter sits over the top-left of the top screen.
- With the WideMelon camera on, the top screen's drawings follow the window: they stay on the frame's middle 256 columns and 192 rows wherever the window puts them, at the window's scale, cut to the picture when panned off its edge (sideways, or up and down into the margin).

### Folder content caps

Kotlin (`impl/LuaScriptFolderContent.kt`) walks the subfolders at launch when any script is on: at most 4 levels, 64 folders (root not counted), 4096 files found, one children query per folder. Path parts outside `[A-Za-z0-9_-]` are skipped (modules and images). Modules: 1 MB each, 2 MB and 256 files total. PNGs: each ≤ 1024×1024, at most 128 files and 4M pixels total, decoded unpremultiplied and sent as ARGB ints. Caps are taken in path order; once one file doesn't fit a total, later ones are left out too, and their names are sent so the error says why.

## Code facts

- **Draw path:** draw calls only record commands into a per-script list (text in a per-script string store, outside the Lua memory cap). `LuaEngine::endFrame()` runs `on_frame_end` and then rasterizes (`scripting/LuaDraw.{h,cpp}`) every running script's lists into the shared buffer in script order (later on top). A script that errors mid-frame shows nothing that frame. `endFrame()` runs whenever `runLuaFrame` ran, so a stopped script is still cleared. A drawn image is anchored in a per-frame registry table until rasterized.
- **Overlay texture:** one per `Frame` (`renderer/FrameQueue.{h,cpp}`), 512×772 (the frame layout at 2×, bottom screen from row 388), created lazily and zero-filled, uploaded on the emulator thread after `RunFrame` and before the frame's `renderFence`, so it can't lag the game image. Only rows with content now or last time are uploaded. `DSRenderer` draws it per screen with a passthrough premultiplied shader (filters never touch it), interleaved: under-screen, its overlay, over-screen, its overlay. With WideMelon it uses the screen's native rect, so it stays on the center 256 (with the camera, `ScreenDrawing.overlay`: that rect in the window, cut to the picture). `ExternalPresentation` draws it too.
- **Overlay in savestate/rewind pictures:** Settings → Display "Show script drawings in save state pictures", off by default, an atomic for the emulator thread. `ScreenshotRenderer` blends it with a 2×2 average (no swizzle: the textures share byte order there); the software path blends on the CPU.
- **Images:** folder PNGs are premultiplied by native and shared, immutable, for the session outside the Lua memory cap (`LuaFolderContent`). `new` images live in Lua's allocator and count. The image metatable is hidden from `getmetatable`.
- **Storage:** `scripting/LuaStorage.{h,cpp}`, a versioned binary codec; the key → encoded map lives in `LuaScript` (`LuaEngineInternal.h`), not the Lua state, so it survives reset and switch off/on. A corrupt blob starts empty (logged) and isn't overwritten until the script writes. Snapshots are encoded only when changed: on `flush()` (end of frame), every 600 frames, when the emulator thread parks for a pause, when a script stops, and at `stop()` after `on_unload`. They go into a global outbox (mutex, outside `MelonInstance`, since `stopEmulation` destroys the instance); an event wakes Kotlin to drain it on IO, and a final drain runs before `stopEmulator()` returns. A snapshot that can't be handed over JNI goes back into the outbox. `impl/LuaScriptDataStore.kt` writes `files/lua-data/<gameKey>/<script>.bin` (temp file + rename). Game key is the game code if it's 4 uppercase letters/digits and not `0000`, otherwise `homebrew-<first 16 hex digits of SHA-256 of the ROM URI>`; if the header can't be read, storage is session-only. An empty store deletes its file; a file over 256 KB is ignored. Not in savestates or rewind; not deleted when the script leaves the folder.
- **Host test:** `app/src/test/cpp/LuaStorageTest.cpp` tests the codec. Built by hand, not wired into Gradle (command under "Testing").
- Layout rebuilds (fold, rotation, swap, script layout switch) carry held touches over to the new controls, so a held button isn't released.

## WideMelon

**How it works.** A width W (even, 256..768; anything else counts as off, `WideMelon::SanitizeWidth`) is set on the GL or compute renderer, and `GPU3D` asks the renderer for it, so a fallback to 256 (W over `GL_MAX_TEXTURE_SIZE`, read once) can't leave geometry squeezed. Each vertex's clip-space X is squeezed by 256/W around the viewport center (`WideMelon::ProjectX`, rounded), so what the game would clip at the sides lands in the extra space; PosTest isn't squeezed. BoxTest tests the native box first and only retries a miss squeezed for a view 8 px wider than W, so a native hit never changes. Culling uses the X from before the squeeze, and the polygon pipeline's timing comes from the native view's clip result (`GPU3D::NativeClipVertices`), so the game sees stock geometry timing. The width is latched at the polygon RAM swap (or while geometry is off), and the targets resize at `RenderFrame`. Display capture and `GetLine` take only the center 256. The compositor outputs `W × scale` by `386 × scale`: the 3D screen's extra columns ("wings") show the 3D image (with `_3dxpos` scroll), the other screen sits centered with black bars. `GetOutputWidth()` is the compositor's width and can lag the requested one; the app sizes its frame texture from it every frame. Savestates don't store the width.

**Code:** core `WideMelon.h`, `GPU3D.*`, `GPU3D_OpenGL.*`, `GPU3D_Compute.*` and `GPU3D_Compute_shaders.h`, `GPU_OpenGL.*` (compositor, wing hold), `GPU_OpenGL_shaders.h`, `GPU2D_Soft.cpp` (per-line flags), `GPU.cpp`. App: width through `EmulatorConfiguration` → JNI → `Configuration.h` → `MelonInstance` (kept there and re-applied on every `updateRenderer()`, which can build a fresh renderer); `Frame` carries `topWidth` to Kotlin; `DSRenderer.kt` (UVs, top rect via `getTopScreenDrawRect`); `VideoFilterPipeline.kt` and `ShaderProgramSource.kt` (filters clamp horizontally only when needed and use a logical width); `ScreenshotRenderer` crops to 256×384 so savestate/rewind pictures are unchanged. Width is applied on OpenGL and Compute; Software uses 256.

**Wings rule, per line.** The 2D line renderer writes flags into the line's control word (`dst[256*3]` in `GPU2D_Soft.cpp`) from the same snapshot it draws the line from, so mid-frame changes and threaded 2D are handled and the wings follow unit A to either screen: bit 18 = 3D in the wings, bit 21 = white wings (screen off or forced blank), bit 22 = unit A drew 3D on BG0 this line, whatever the windows do (only used by the wing hold). Master brightness leaves bits 5–13 free; 8–12 and 19–20 are unused since the wing planes took over the fade.

**Wing planes.** On a line with bit 18, `SoftRenderer::DrawWingPlanes` also stores planes 0–2 for one wing pixel per side. If the edge column (0 for the left wing, 255 for the right) has the 3D on top with only the backdrop under it, the wing gets that column's planes and `WingPixel()` composites them with the wing's 3D pixel through `CompositePixel`, as the edge pixel would be: blended with or faded over the backdrop, with the edge's compmode and window effects. The wing's transparent 3D shows the backdrop only where the edge visibly does too: if the 3D one native pixel in from the edge (column 1 or 254, with the X scroll, at any scale) isn't transparent, a transparent wing 3D pixel is taken as opaque (alpha 31 for compmode 4, 1 for 0, 2 and 3), so it shows the 3D clear color as before step 1. That's for a squeezed screen-wide 3D quad (Contra 4's "Licensed by Nintendo" screen and its fades), which leaves the wings' 3D transparent while the edge's isn't; the CPU never sees 3D alpha. It's one pixel in because squeezed geometry ending at the screen edge can miss column 255 (that screen shows a 1-px white line there, from before step 1). On lines where a 2D layer is over or under the 3D at the edge, the planes carry `GPU2D::WingRaw3D` and the wing looks exactly as before step 1: the 3D as it is, transparent or not, with the BLDCNT fade for BG0 as first target. The planes sit after each screen's 192 lines in its framebuffer (`GPU2D::AccelWingPlanesStart`), so they swap with POWCNT and always belong to the frame being composited, also with threaded 2D and the Blit after the readback. The compositor uploads them as `WingPlanesTex` (6×384 `RGBA8UI`, unit 10). Lines without bit 18 are unchanged (black, white or held).

**Windows.** With wide view on, native columns 0 and 255 take their neighbor's window mask, which removes a 1-px backdrop seam (also in capture). With any window on, a line gets 3D wings only if BG0 shows at column 0 or 255 (WINOUT and the OBJ window included), so a window letterbox blacks the wings out with the middle. One wings bit per line: BG0 at one edge gives 3D on both sides. A window cutting BG0 mid-line doesn't affect the wings. A wing that carries on its edge column follows that column's window effects; one that shows the 3D as it is ignores the window's effect-enable bit.

**Dual-screen wing hold.** Games with 3D on both screens (Phantom Hourglass, Mario Kart DS) move unit A every frame, so each screen's wings would flash at 30 Hz. The GL compositor keeps a copy of the output's wing columns (`HeldWingsTex`, blitted after drawing while both halves have had 3D lately). When unit A's wings appear in the other half, a half that had its own in the last 2 frames reuses them, only on lines that had bit 18 in the copy and would be black now, for at most 2 frames in a row; a width or scale change drops the copy. The half unit A is in comes from bit 22, so a window blacking out all of unit A's wings doesn't stop the hold. Single-screen 3D games never copy or hold.

**Adreno gotcha:** held lines reach the shader as bit 13 of the line's control word (`GLCompositor::PrepareWingHold`), because Adreno never applied an earlier `uvec4 uWingHold[3]` mask to word 0, which gave flickering black notches on Phantom Hourglass's top screen; keep the flag in the control word.

**Lesson:** for wing bugs, a per-line dump on the phone (output, held texture, 3D texture and each line's control bits) found what code reasoning didn't, so write a new one rather than guess (the old one is gone).

**Known limits:** edge pop-in in games that cull on the CPU or with PosTest; ortho 3D HUDs and full-screen 3D quads stay 256 wide; 2D-only scenes get black wings; transparent 3D shows the backdrop in the wings only where the edge visibly shows the backdrop (3D on top and transparent there, the backdrop under it), otherwise still the 3D clear color; BoxTest, the polygon RAM counts and limit (and its DISP3DCNT overflow bit) make it visible to the game; loading a state made at another width gives a frame or two of squeezed geometry.

**Compute renderer.** Same width rules, latch and `WideXAdjust` as GL. Its work buffers and shaders are built for the width (`ScreenWidth` etc. are shader constants), so a change of the output width recompiles all 33 shaders inside `RenderFrame`, a short pause on fold or rotation. The dispatches need whole coarse tiles (`ScreenWidth/CoarseTileW`) and whole bin-mask clear groups, so the internal width is rounded up until both divide (256 always does); geometry sits at the left, the final pass doesn't store the extra columns on the right, and the 3D texture is exactly W × scale. The final pass writes only the center 256 to the low-res image that capture and `GetLine` read. At 256 the shaders get no extra defines, so they're unchanged.

### Camera

Stage 1 of the camera in [docs/plan-widemelon.md](docs/plan-widemelon.md) ("Camera: pan and zoom"): display-side only, the game's camera never moves. Mods tab, under widescreen: Camera (off by default), "Zoom out up to" (426, 448, 512, 640 or 768 DS pixels, 512 by default) and "Return to center when moving" (on by default), stored as `RomModsConfig.wideCamera`, `wideCameraMaxWidth` and `wideCameraReturnToCenter` (new keys, so older configs read as off). The last zoom picked with the Camera Zoom hotkey is kept per game too (`wideCameraZoom`, written from the emulator through `EmulatorViewModel.onWideCameraZoomPicked` into the ROM that camera session launched), and the camera starts there the next time it comes on. The view model's `WideCameraState` carries a session number, the settings and the start zoom apart from the settings, so a pick never counts as a settings change (which drops held input), a recreated activity's controller starts at the latest pick, a pick still on its way during a ROM switch is dropped, and a new session resets the controller even if the off state between sessions was conflated away; auto-1x and script holds override it on screen without changing it, and pinches and scripts' zooms aren't kept.

- **Two widths.** The layout keeps its show width Wd; the core renders at Wr = max(Wd, the max zoom-out) (`WidescreenLaunch.getRenderWidth`, sent where the width always went). Camera off, or a variant that isn't wide: Wr = Wd and nothing changes. A max zoom-out no wider than Wd counts as the camera off for that variant (no room to zoom or pan), and the Mods tab only offers widths past the shown one, with a note when the stored one isn't. The core only adds `OutputLayout::TopWingLines`: the top screen's lines with 3D wings, counted in `GLCompositor::PrepareWingHold` from control word bit 18 plus the lines the wing hold fills (`WingHoldLines`, which are only ever black lines), carried per `Frame` to Kotlin with the frame.
- **The window.** `WideCameraController` moves `domain/model/camera/WideCamera` (unit-tested, no Android) once per presented frame on the render thread (`FrameRenderCoordinator`), so every surface shows the same `WideWindow` [x, x + w) of the Wr-wide top half. `getScreensDrawing` shapes the screen's rect for Wd, maps the window across it and letterboxes it top and bottom when w > Wd. When only the window moved, `DSRenderer` refills its quads into a reused buffer (`glBufferSubData` into storage made once) and rebuilds the shadows only if a drawn rect changed; the camera reuses its input and its window at rest, so a moving camera allocates its new window and the drawing's few small objects per frame. The bottom screen and touch are unchanged.
- **Controls.** Right stick X pans (dead zone 0.2, 300 DS px/s, eased), unless the right stick (`AXIS_Z`/`AXIS_RZ`) is mapped to an input, and only from a device whose `AXIS_Z` and `AXIS_RZ` are a centered pair that has been seen resting in the middle (`CameraStickReader`, so a trigger on `AXIS_Z` never pans). Not while a menu or dialog is over the game; opening one drops the held stick, D-pad and touch. Camera Zoom is one mappable hotkey (Input setup), the right stick's click (`KEYCODE_BUTTON_THUMBR`) by default, like PokeDaisy's Expand: each press goes to the next step, in steps of 0.25 with the widest view as its own last step, and from the widest back to 1x (1, 1.25, 1.5, 1 with a 1.5 widest view; `WideCamera.cycleZoom`). After a pinch, a press goes to the step above. Holding it doesn't repeat (`InputProcessor` drops the key's repeats, also the first one after a menu closes with the key still held). Presses during auto-1x still count and show once it ends, and a press before the first wide frame (at launch, or with a width change on its way) waits for it; presses while the camera is off, or while a script sets the zoom, are dropped. Stored controller configs keep their mapping: an entry for an input this version doesn't know (such as the earlier test builds' `CAMERA_ZOOM_IN` and `CAMERA_ZOOM_OUT`) is dropped on load instead of failing the whole file (`InputConfigDto.input` is the name as text), and a config with no Camera Zoom entry gets R3 unless R3 is already mapped to something (`withDefaultCameraZoomKey`, used on load and by the v33 migration, which would otherwise write the hotkey as unmapped; unit-tested). Nothing else in the defaults uses R3. One finger dragging the DS top screen pans, two pinch, and the picture moves 1:1 with the finger (the drag is measured against the drawn picture's width). That's only while the top screen is the wide one (not swapped) and its rect doesn't overlap the touch screen's, since a top screen stacked over the touch screen would take the game's touches; such layouts have the stick and hotkeys only. A listener change mid-gesture drops the touch. With the stick idle and the D-pad or left stick held, the pan eases back to the middle if return to center is on.
- **Lua and the right stick.** A script that reads `melon.input.stick("right")` for its own use (aiming, say) also pans the camera; it should take the pan over with `melon.wide.pan(...)` (`pan(0)` keeps the middle) while it uses the stick.
- **Back to 1x.** Straight to 1x in the middle when the frame has no top-screen wing lines, with the screens swapped (the wide screen is then the touch screen), or while a script holds native. Dual-screen 3D games (Mario Kart DS, Phantom Hourglass) aren't held: their held lines count as wings, and the held wings cover the whole render width. The player's zoom comes back (eased, pan centered) once the frame has been free of those for 0.25 s.
- **Lua:** `melon.wide` above; `melon.wide.camera()` reads atomics the controller sets through `MelonEmulator.updateWideCamera`, on the first presented frame of each controller (so a recreated activity never leaves the old values) and whenever the window moves.
- **Stage 2, vertical zoom-out (app half).** The core renders M rows of 3D above and below the top screen (`GLRenderer`/`ComputeRenderer::SetViewMargin`, next to `SetViewWidth`), so zooming out fills the screen instead of letterboxing. The app picks M with the width: `WidescreenLaunch.getRenderMargin` = ceil(96 · (Wr/Wd − 1)) in whole numbers, at most 128 (`MAX_WIDE_VIEW_MARGIN`; 342 shown from 512 gives 48), and 0 with the camera off, for a variant that isn't wide or with no room to zoom. Like Wr it only changes with the shown width, never per zoom step. It goes out with the width as one value: `EmulatorManager.setWideView(width, margin)` → `MelonEmulator.setWideView` → `MelonInstance::setWideView` (packed in one atomic, so a frame never gets the new width with the old margin), and at launch `EmulatorConfiguration.wideViewMargin`. `debug.melonade.widey` = 0 (`GPU::WideY`) has the core render no margin for A/Bs.
  - **Frame layout.** The top screen's half of the frame texture is Hr = 192 + 2M rows, then the 2 gap rows, then the bottom screen's 192; DS line y of the top screen is row y + M, and M = 0 is the old 386 row layout. `MelonInstance` sizes the frame from `GetOutputWidth()` and `GetOutputMargin()` (the latest output frame's, which lag the requested ones together), and Software is always M = 0. Each `Frame` carries `topScreenMargin` to Kotlin (`FrameRenderCallback`, `PresentFrameWrapper.topScreenMargin`/`topScreenHeight`). `FrameTextureLayout` (unit-tested) has the screens' v coordinates, exactly the old ones at M = 0; the filters get the rows through the `frameLayout` uniform (`Shader.setTopScreenHeight`: the top half's end, the bottom screen's start, the split between and the frame's rows), with the old constants kept where M = 0 so camera off draws bit for bit as before. Screenshots and savestate pictures still crop to the native 256×384, skipping the margin (`ScreenshotRenderer`). The Lua overlay texture keeps the old layout.
  - **The window** gets a y and a height (`WideWindow.frameHeight`, `y`, `height`, `offsetY`): h = 192 · zoom clamped to Hr, letterboxed only by what Hr can't cover (`getScreensDrawing`), and the vertical pan is clamped to (Hr − h)/2 and eases back to the middle like x. Without a window the top screen shows rows M..M+191 (`ScreenDrawing.topRow`/`bottomRow`), and at 1x the window is those rows with the same rects, so the output cap (`nativeRectAt1x`) is unchanged. The bottom screen never has a margin, so swapped it shows all its rows.
  - **Controls.** The right stick's Y (`AXIS_RZ`, down is down) pans vertically with the same dead zone and speed, and a drag's Y moves the picture with the finger (measured against the drawn picture's height). Return to center needs both stick axes idle.

### Wide layouts

The player places the wide top screen in the normal layout editor. Each layout variant (`UILayout`: folded/unfolded, portrait/landscape, displays) has its own `wideAspect: WidescreenAspect?` (null = normal 4:3 at 256). `WidescreenAspect` has stable keys 16:10, 16:9, 20:9, 21:9 → widths 308, 342, 426, 448 (`192 × ratio`, rounded to even). A layout is "wide" when any saved variant has a ratio. Old layout-level `wideAspect` values are copied to the saved variants on load.

- Editor: the top screen's Wide chip sets and re-shapes only the variant being edited (same rule as automatic placement); its aspect lock offers the variant's ratio next to 4:3, 16:9 and Free. Lists show "Wide 20:9", or "Wide" when variants differ.
- Mods tab with widescreen on: "Wide layout" is Automatic or a layout marked wide (`LayoutSelectorActivity`, wide-only filter). Automatic uses the tab's own ratio (16:9 default) with automatic widening; with a wide layout the ratio is "set by the layout". The row says it needs OpenGL or Compute when the global renderer is Software.
- Launch: widescreen on + wide layout found + OpenGL or Compute → that layout (`EmulatorViewModel.startObservingLayoutForRom`, `wideLayoutId ?: layoutId`). No wide layout found → normal layout with automatic widening. Widescreen off or Software → 256 for the session. Lua `set_layout` and player picks still override.
- During play the width follows the active variant: on fold, unfold or rotation Kotlin sends the new width, applied on the emulator thread through `SetViewWidth` on the GL or compute renderer (no rebuild); a frame or two shows the old width in the new rect.
- Top rect: a rect at least as wide as the frame (2 px tolerance) is used as drawn, frame centered at its exact aspect. Otherwise it's widened around its center up to the surface edge without covering the bottom screen's rect, then shrunk to fit; a bottom screen sharing rows with the top stops the widening at its near edge. An unedited variant (from the default 4:3 layout) still gets automatic widening. Touch is untouched.

## Testing

`LuaStorageTest.cpp` builds with any C++17 compiler, for example from `app/` with MSYS2's MinGW, in an empty folder of your choice:

```
gcc -c -O1 -Isrc/main/cpp/lua $(ls src/main/cpp/lua/l*.c | grep -v -e /lua.c -e /luac.c -e /lstrlib.c) src/main/cpp/lua/patched/lstrlib.c
g++ -std=c++17 -O1 -Isrc/main/cpp/lua -Isrc/main/cpp src/test/cpp/LuaStorageTest.cpp src/main/cpp/scripting/LuaStorage.cpp *.o -o lua-storage-test
./lua-storage-test
```

OpenGL, and so all WideMelon output, is phone-only: the emulator has no GLES 3.2, so there it can only check the Mods tab and layout UI. Not phone-tested yet: the wings' window handling, and script drawings in savestate pictures.
