## Why, and what to expect

On the Z Fold 8 the emulator thread uses about 10 ms of a 16.7 ms frame (Phase 0 profile in `PERF-NOTES.md`, 2026-11-01), so games already hold 60 there. The gains this plan is after are battery and heat, weaker phones (the OnePlus 7 Pro manages 26 fps in the compute capture scene at 4x), and the heaviest menus that aren't perfectly smooth. Keep a change only if it measurably helps one of those.

Shares of the emulator thread from that profile (OpenGL 4x, threaded 2D off): software 2D 33%, bus/memory/interpreter 29%, 3D geometry 11%, Adreno driver 10%, JIT code 8%.

How to measure: perf log sessions (Settings → Performance → Diagnostics) in a 3D-heavy and a 2D-heavy scene (White 2's title and overworld, Dark Dawn's capture scene), OpenGL and compute, a fresh game start per run. Compare cycles per frame rather than ms, and check logcat for `limitCPUFreq` and `thermal_core` before trusting a slow run (the perf logger workflow in `PERF-NOTES.md`). Repeat on the OnePlus 7 Pro when it's reachable, since that's where gains show most.

## Part 1: build flags

Before this, every native build was `RelWithDebInfo` (`-O2 -g`) and the core's own `-O3`/LTO only applied to CMake's `Release` configuration, which we never use. Now each flag has its own Gradle property, passed by `app/build.gradle.kts` to `app/CMakeLists.txt` as `MELONADE_O3`, `MELONADE_LTO` and `MELONADE_ARMV82` (set before the subdirectories so the core gets them too). Since the 11-03 Fold profile all three are on by default (pass `-PnativeO3=false` and so on to turn one off). Together they cut emulator-thread cycles per frame by 2.4% in the White 2 title screen, with no fps change there; each flag alone is not measured yet (PERF-NOTES "Native build flags"):

1. **`-O3`** (`nativeO3`) for every native target, the core included.
2. **ThinLTO** (`nativeLto`), through `add_compile_options`/`add_link_options` rather than CMake's IPO, which sidesteps the app's old `cmake_minimum_required` and CMP0069.
3. **armv8.2-a** (`nativeArmv82`, arm64 only). The catch is that the APK no longer runs on armv8.0 phones (older Cortex-A53/A57/A73 SoCs) that still meet minSdk 29, so keeping it is the user's call, not just a numbers call. The Shield hit exactly this; [plan-shield.md](plan-shield.md) step 0 has the tentative rollback. The 32-bit `armeabi-v7a` build on GitHub releases is unaffected.

When testing a flag: run the JVM tests and `LuaStorageTest`, boot a game under OpenGL, compute and software, check that every `JNIEXPORT` function is still exported (`llvm-nm -D` on the `.so`) and that the JIT still turns on. Keep a flag only if heavy scenes use clearly fewer cycles per frame (a few percent, beyond noise); if one pays but makes incremental builds painful (most likely LTO), make it release-only.

**PGO, tried (11-16), off by default.** `-PnativePgo=generate|use` is in (`tools/pgo/README.md` has the steps, including the release-variant training build). A Pixel-only profile made the OnePlus's White 2 Compute 2x 1.1 ms/frame slower. Adding ~8 min of OnePlus training (Compute 2x and GL) fixed that: the merged profile cuts emulator-thread CPU 3–11% in Dark Dawn and 3% in White 2 on the Fold and OnePlus, with no regression in the six scenes measured. The first release profile (Pixel + OnePlus, 10 sessions) gives −4 to −6% emulator CPU in Dark Dawn, White 2 within ±2%; the OnePlus's White 2 Compute 2x tail was worse in one pass. On 11-17 the user decided to keep PGO off by default: the release profile stays local, and `-PnativePgo=use` turns it on. See PERF-NOTES "PGO".

## Part 2: code-level, biggest first

4. **Threaded 2D's busy-wait. Done (11-04), switch `lateblit`, on by default.** With threaded 2D on, `GPU::Wait2DJobs` busy-waited for 11% of the emulator thread, 92% of it at the line-192 Blit barrier. Moving the Blit later halves the wait and cuts emulator cycles 10%, but the clock drops 9% with it, so frame times don't improve and p99 is 0.4 ms worse. Kept on for the lower clock (PERF-NOTES "Threaded 2D late Blit"). **Threaded 2D stays off by default (11-16 recheck, after `heldworker=63`):** every run on all three phones held 60 fps; White 2 title work drops 1.3 ms on the Fold and ~0.3 on the others, but total CPU rises 10–35% (the 2D thread uses 2.4–3.7 ms/frame), tails go both ways, and Dark Dawn's capture scene doesn't change (PERF-NOTES "Threaded 2D default check").
5. **Held 2D lines in capture scenes. Done (11-16), switch `heldworker`, default 63 (only acts with threaded 2D on).** In capture frames all 2D ran on the emulator thread, about 2.1 ms of 12–13 ms per frame on the White 2 title. Just moving it to the 2D thread saved nothing, because the two threads spun waiting on each other; bits 4 (wait at the Blit), 8 (POWCNT and other LCDC reads don't wait), 16 (engine B in batches) and 32 (back off when a game waits early) fixed that. `63` is output-identical (HASH2D/HASH3D on the desktop and phones) and doesn't regress anywhere: White 2 work −1.1 ms on the Fold, OnePlus compute 2x frames over budget 98 → 25. Hi-res capture is unaffected. See PERF-NOTES "Held 2D lines on the 2D thread".
6. **The emulator thread's CPU clock. Shelved (11-16)** by the user's call. The thread is only about 60% busy, so Samsung's power manager keeps its clock low, which costs smoothness more than average speed. The two untried ideas are in the ADPF section of `PERF-NOTES.md`: an opt-in lower ADPF target, or spinning the end of the pacing wait. Also still open: why a second busy thread lowers the emulator thread's effective clock even on another cluster.
7. **Bus, memory and interpreter (29%).** Call graphs (11-16, Pixel 8, PERF-NOTES "JIT and bus call graphs"): almost nothing is interpreted. The cost is the JIT dispatcher (`Execute` loop + `LookUpBlock`, ~8%), slow memory paths called from JIT code (~6.6%, `SlowBlockTransfer9` first), the scheduler (~5%) and DMA (~2%). Core code, so changes should stay close to upstream.

   **Left:** the scheduler loop (~5%) and DMA (~2%). Not scoped yet.

   **Done, and what it showed:**
   - **LDM fast path (core `1af8c11b`, switch `ldmfast`, on by default).** The A64 JIT only compiled the block-transfer fast path for stores, so every LDM and Thumb POP went slow. Hashes identical on both phones, but `SlowBlockTransfer9` only dropped ~4–7%, no frame-time change (PERF-NOTES "LDM fast path on ARM64").
   - **Where the slow ones go (core `71d13535`, `ldmstats`).** 66–82% of ARM9 slow block transfers come from fast-path sites the fault handler patched (I/O, VRAM, probably writes to code pages), which then stay slow forever even for later DTCM or main RAM calls. Data: `perf_logs/2026-11-16-ldmstats/`.
   - **Direct path (core `124fd279`, switch `ldmdirect`, on by default).** `SlowBlockTransfer9/7` copy straight to host memory when a transfer stays in one ITCM/DTCM/main RAM/WRAM7 region. Bit-identical. The x64 desktop JIT gains a lot (White 2 75 → 123 fps), the Pixel barely moves (Dark Dawn +2.6% uncapped). So on ARM64 slow transfers aren't where the time goes. The desktop gain is probably MinGW's emulated TLS making each `NDS::Current` read a call (unproven; a desktop profile with `--ldmdirect 0` would show `__emutls_get_address`). The DSi branches are code-reviewed only. Re-checking patched sites at run time wasn't tried and isn't worth it after this.
   - **Dispatcher stub (switch `jitdispatch`, on by default).** One stub per CPU in generated code does the cycle add, `StopExecution` and region checks and the block-table lookup, then `br`; anything unusual falls back to `ARM_Ret`. +113 lines in the core, identical to `jitdispatch=0` in jitverify over 3000 frames in all 21 DS ROMs. In jitverify `ARMv5::Execute` went 7.5% → 2.4%, but in the app it's about 1% (cycles per frame −0.9% Pixel White 2, −1.4% OnePlus White 2), with p95, p99 and 1% lows unchanged. Kept on since it costs nothing. Data: `perf_logs/2026-11-16-jitdispatch/`, `logs/jitverify/dispatch/`.
   - **Block linking, shelved.** Upstream had linking on x64 in 2020 (`3787bab1`) and removed it in the fastmem refactor (`e335a8ca`, `65be1840`), with no reason recorded. The case for it was that the stub's shared `br` mispredicts a lot, and it doesn't: simpleperf on the Pixel's X3 core puts all dispatch-path mispredicts at under 0.6% of cycles, and the stub adds none (`perf_logs/2026-11-16-jitdispatch-bmiss/`). Linking would also have to keep the per-exit cycle and target check to stay exact, so it could only remove the lookup, roughly another 1% for +250-350 lines and medium risk. Not worth it unless the dispatcher shows up again in a different workload. Inlining `LookUpBlock` alone is under 10 lines, for about 1%. Raising `MaxBlockSize` past 32 changes timing and hashes.
   - **JIT timing fixes (core `d7f766b3`, `d2a77eab`).** `SetMaxBlockSize` passed LiteralOptimizations as BranchOptimizations; A64 ARM7 multiply timing and Thumb MUL were wrong (all multiplies now match the interpreter over 280 M cases); A64 `Comp_AddCycles_C(bool)` was inverted against x64, and a conditional interpreted fallback could drop Cycles and CPSR on an early exit. Pixel smoke tests showed no fps change. Still differs: x64 skips C on skipped conditional instructions (upstream too), and the interpreter's Thumb MUL only stops early on leading 0s, which may not match hardware. No `JIT far memory full` resets showed up in any 11-16 run.

   **Verification: `tools/jitverify` (built 11-16).** A headless runner that writes per-frame hashes of screens, audio, timestamps, registers and memory; usage is in `tools/jitverify/README.md`. The reference is the same backend before vs after a change: A64, x64 and the interpreter all differ from frame 0 in timing. Two runs are byte-identical on the PC, the Pixel 8 and the OnePlus 7 Pro, and Pixel matches OnePlus, in White 2 and Dark Dawn over 3000 frames, with and without mid-run resets (`logs/jitverify/v2/`). Still worth adding: gameplay savestates (overlays, battles), Pokemon B/W (code in VRAM), Mario Kart DS or MPH (timing), and one DSi title.
8. **Adreno driver time (10%).** Fewer GL calls and state changes per frame would trim it a little; the bigger answer is the Vulkan renderer in [plan-vulkan.md](plan-vulkan.md), which has its own gate.
