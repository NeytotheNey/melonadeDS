# Plan: a SWI test ROM for FreeBIOS

Status: DS and DSi mode built and run (2026-11-02); results in the core's `freebios/UPGRADE_PLAN.md` ("SWI test ROM" and "SWI test ROM, DSi mode"). The phone SoftReset log is still open.

## Why

FreeBIOS (our clean-room DS BIOS replacement, in the core's `freebios/`) has fixes that no game on hand ever calls. On the phone, 13 games ran fine with it, and the PC harness found no result differences for Dragon Quest IX or Advance Wars. But none of the ROMs we have calls SoftReset (SWI 0x00), HuffUnComp (0x13), RLE-to-VRAM (0x15), or IntrWait with r0 = 0. So those paths are only checked by rebuilds, disassembly of our own images and a Python model.

The fix is to stop waiting for the right game. Write our own small DS program that calls each BIOS function with known inputs and stores what comes back. Then run it in the PC harness once with the user's official BIOS and once with FreeBIOS, and diff the results. That's black-box testing, so it keeps the clean room. It also stays in the repo as a regression test for later FreeBIOS changes.

The open items this answers are listed in the core's `freebios/UPGRADE_PLAN.md` ("Open items" and "Next testing ideas").

## Clean-room rules (read first, they're strict)

- **Never inspect Nintendo's BIOS.** The official dumps (`C:\Dev\swi-harness-data\bios\`, `...\dsi\`, and the NAS share) may only be loaded so the emulator can run them. Never disassemble, hexdump or string-search them, and never use Ghidra on them.
- **No test may copy BIOS bytes into the results.** Don't point GetCRC16 at the BIOS, don't use a BIOS address as a CpuSet/CpuFastSet/decompression source, and don't dump what GetSineTable/GetPitchTable/GetVolumeTable return. Where a test needs one of those (for example "a source in the BIOS range is rejected"), store only a match flag or a hash of the destination, never the bytes. Table SWIs are compared by hash only.
- **Specs are hypotheses.** There's a GLM-written behavioral spec for the DSi BIOS. Coding subagents get only the trimmed copy, `C:\Dev\NDS BIOS & Firmware\DSi\DSi_BIOS_SWI_Behavioral_Spec.redacted.md`, never the original next to it. It's outside the repo; don't copy it in. Its claims (for example "0 ÷ 0 returns 1" or the IntrWait "leftover bits" rule) are things to test, not facts.
- **FreeBIOS only changes from evidence:** a harness diff against the official BIOS, cross-checked with GBATEK (https://problemkaputt.de/gbatek.htm and its split pages). This task builds the test and reports; fixing FreeBIOS is a follow-up the user approves.

## What exists already

- **The harness** is in the core's `tools/swi-harness/`. It's a headless PC build of the core, with an SWI logger behind `MELONADE_SWI_LOG` and `swi_diff.py`. Build it with MSYS2 MinGW:
  `export PATH=/c/msys64/mingw64/bin:$PATH`, then
  `cmake -G Ninja -S tools/swi-harness -B /c/Dev/swi-harness-data/build -DCMAKE_BUILD_TYPE=Release -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++`
  and `cmake --build /c/Dev/swi-harness-data/build`.
  Run `swi-harness.exe <rom.nds> --bios official <dir> | --bios free --frames N --out <dir>`. Useful options: `--console dsi --dsi <dir> --nand <copy>`, `--rtc`, `--tap KEY@FRAME` and `--dump-mainram`; the full list is in `Usage()` in `main.cpp`. Inputs are in `C:\Dev\swi-harness-data\`. Each DSi run needs its own NAND copy, deleted afterward.
- **The toolchain:** the Android NDK's clang 19 at `C:\Tools\android-sdk\ndk\28.0.13004108\toolchains\llvm\prebuilt\windows-x86_64\bin` (clang, ld.lld, llvm-objcopy). `freebios/build.sh` shows how we build bare-metal ARM images with it.
- **The direct boot** in our core sets up a DS-mode program the way the firmware would. It loads the ARM9/ARM7 binaries from the cartridge header and starts them, so the ROM needs no Nintendo boot code.

## What to build

All of it goes in the core: `tools/swi-testrom/`.

1. **The ROM.** It has its own minimal startup code for both CPUs, written from GBATEK: stacks, IRQ vector, and an IRQ handler that acknowledges IF and ORs it into the BIOS IRQ flag word (ARM9 at DTCM+3FF8h, ARM7 at 0380FFF8h, as GBATEK describes). It needs a test table, and a small script that writes the NDS header (GBATEK's cartridge header layout, header CRC via CRC-16) and packs the two binaries into a `.nds`. The build must be reproducible from sources with one script, like `freebios/build.sh`. Test data (LZ77, Huffman, RLE, Diff streams) is generated by our own Python encoders written from GBATEK's formats.
2. **The results.** Each test writes a fixed-size record to a results area in main RAM: test id, r0-r3 after the call, CPSR flags, a hash of the output buffer, the start of the output buffer (game data only), and a cycle count from cascaded timers. A "done" marker goes at the end. Read the area back with `--dump-mainram`, or add a `--dump-range addr len` option to the harness.
3. **Hangs.** Some cases are expected to hang on real hardware (Div by 0 with a nonzero dividend, invalid SWI numbers). Put those in separate modes, picked by a build flag or a value the harness pokes before boot. Then a hang only loses that one case, and the report shows "didn't finish by frame N".
4. **SoftReset.** This is its own mode. Point the entry address at 027FFE24h (ARM9) / 027FFE34h (ARM7) to a probe that records sp for svc/irq/sys, lr, CPSR, the CP15 control register (ARM9), whether the 200h area was cleared, and r0-r12. Run it with DTCM at its default and with DTCM moved, the way games do.
5. **A report script.** Pair the official and FreeBIOS result dumps by test id and list mismatches first (registers, output hash, first differing output bytes), then cycle differences on their own. Plain text, in `C:\Dev\melonDS-android\logs\swi\testrom\`.

## Test list (DS mode first)

Take inputs from GBATEK and from the edge cases in `freebios/UPGRADE_PLAN.md`. The redacted DSi spec's "Test inputs" sections are a good checklist too, since most functions match between DS and DSi. Run each test on the CPU(s) where the SWI exists.

- **Div:** signs, remainder sign, INT_MIN ÷ −1, 0 ÷ 0, and x ÷ 0 in the hang mode. **Sqrt:** 0, 1, 15, 16, 0xFFFFFFFF, 2<<30.
- **CpuSet:** 16/32-bit, copy and fill, count 0; check r0/r1 after. **CpuFastSet:** count 0, 1-7, 8, 9, large, fill; also junk in bits 21-31.
- **BitUnPack:** 1→4 bpp, the zero-data flag, an odd unpacked size.
- **LZ77 WRAM/VRAM:** size 0, displacement 0, odd size, a stream ending mid-flag-group.
- **HuffUnComp:** 4- and 8-bit data, sizes that aren't a multiple of 4, single-node trees, deep trees.
- **RLE WRAM/VRAM:** a run that overshoots the size, an odd size, odd VRAM start and end.
- **Diff8/Diff16 (ARM9):** count 0, wrap-around.
- **GetCRC16** over RAM only: length 0, odd length, both seeds; check r1/r3 after.
- **WaitByLoop:** 0, negative, a small count (cycles only).
- **IntrWait / VBlankIntrWait / Halt:** r0 = 0 with the flag already set, r0 ≠ 0, the wanted flag alone vs with another flag pending, the IME value after. On both CPUs.
- **Table SWIs (ARM7):** compared by hash only, including out-of-range indices.
- **Invalid numbers** (0x1E, 0x2A+, mirrors above 0x3F), in the hang mode.
- **SoftReset**, as above.

## Later: DSi (TWL) mode

Our TWL FreeBIOS build isn't used by the app, so this comes second. It needs a TWL-flagged header so the game boots in DSi mode, and a harness option to load the TWL FreeBIOS (`FreeBIOSGetTwlArm9/7()`) in place of the DSi dumps. Then it reuses the same tests, plus the DSi-only ones the redacted spec covers: SHA-1 (0x24-0x29), RSA (0x20-0x23), CustomPost, the ARM7 source-range check, and the DSi IntrWait rules. RSA and SHA-1 are stubs in our TWL build today.

## Optional: a SoftReset log on the phone

A debug-build log line when a game calls SWI 0x00. It would show whether games that return to their title (Dragon Quest IX after a quicksave) use the BIOS reset or their own code. This is small and separate from the ROM.

## Done when

- The ROM builds from sources with one script, and the harness runs every mode with both BIOSes in DS mode.
- The report lists every difference between the official BIOS and FreeBIOS, each checked against GBATEK, with a proposed fix or "matches GBATEK, keep".
- The core has the sources and scripts committed (once the user says to commit), with no BIOS data in them, and `freebios/UPGRADE_PLAN.md` points to the test and records the results.
- Coding went through a subagent and was reviewed by a fresh one (the usual workflow).
